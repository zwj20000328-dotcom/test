# 检查点、容错与弹性训练

## 1. 问题定义与为什么它是存储问题

大模型训练的持久化状态不是"模型"，而是"参数 + 优化器一阶/二阶矩 + RNG 与数据加载游标"，体积通常是参数量的数倍。与此同时，每步计算时间随算力下降，状态落盘时间却受限于集群存储带宽。二者剪刀差的直接后果是：检查点频率越高，回滚窗口（RPO）越短，但写放大与训练停顿越大。AccelPact 在 1.216B 参数 decoder 上的测量把这一点量化了：每步都做异步检查点会带来高达 +656.7% 的延迟开销、32.5 GiB 主机内存占用、3.39 TB/hour 的存储流量 [arXiv:2609.18178v2]。这就是所谓"存储背压"（storage backpressure）——容错从计算问题变成了写入带宽、放置与元数据问题。

关键指标有五类：(1) 无故障时的检查点开销占比（goodput 损失）；(2) 恢复时间 MTTR 与回滚步数；(3) 单位时间存储流量与峰值带宽占用；(4) 持久化容量与副本数；(5) 作业是否必须终止。TierCheck 指出失效是异构谱：从单 GPU 崩溃到整集群断电，单一存储层无法同时优化"写开销"与"恢复速度" [arXiv:2605.17821v1]；PHOENIX 则把"无故障开销 vs 恢复延迟"显式描述为一条 Pareto 前沿 [arXiv:2607.01646v2]。需要区分的是，本方向文件中另有一批 activation checkpointing 工作（如 Mist [arXiv:2503.19050v1]、[arXiv:2506.21833v2]），那是用重算换显存的训练内存优化，与持久化容错不是同一问题，本文不纳入。

## 2. 技术流派

### 2.1 分层放置：把失效谱映射到存储层

核心思想：不同故障的影响范围不同，恢复所需数据的新鲜度也不同。用内存/对等节点承载"最新、最小"的差分状态，用远端持久层承载"旧、大"的基座状态。

- [arXiv:2605.17821v1] TierCheck: Tiered Checkpointing for Fault Tolerance in Large Language Model Training。三层设计：本地与对等内存保存轻量差分检查点用于局部快速恢复，重量级基座检查点异步迁移到远端持久存储；跨层保持严格全局一致性且不暂停训练，恢复时做集群感知的检查点重建。摘要称在最大 40B 参数模型上评估，但收益数字在 900 字符处被截断（"TierCheck achi…"），**摘要未给出**。局限：依赖对等节点有足够空闲内存且故障不相关；跨层一致性协议本身有元数据开销。
- [arXiv:2607.01646v2] PHOENIX: Resilient LLM Training with Hot-Swapping via Zero-Overhead Checkpoint。用热替换把故障节点换成备用节点而不终止整个作业；关键是在关键路径之外做内存检查点，使无故障执行几乎零开销，同时避免"少数节点永久失效"时的长恢复。摘要被截断，未给出加速比。局限：需要预留 spare 节点，等价于用集群利用率换 MTTR。
- [arXiv:2401.14351v2] ServerlessLLM。推理侧的同构思路：利用 GPU 服务器近端存储做本地检查点，设计加载优化的检查点格式与多级加载，避免远程下载；并支持推理实例活迁移与启动时间优化调度。局限：面向推理冷启动，不解决训练态一致性。
- [arXiv:2606.17787v1] LUMEN。把 serving 故障恢复建模为跨三个决策点的负载感知协调问题，其中包括故障前的检查点放置；指出既有方案要么从头重跑请求，要么从固定邻居恢复 KV cache，都没考虑当前集群负载。摘要截断，无量化结果。

共同假设：内存/邻居余量充足、故障域相互独立。失效场景：机架级或供电级相关故障会同时打掉"本地 + 对等"两层；内存吃紧时差分检查点会被 OOM 路径清掉。

### 2.2 压缩与选择性持久化：少写

核心思想：检查点内部存在大量冗余——相邻步差分稀疏、层间更新不均匀、MoE 专家激活稀疏——因此只写"变化的部分"。

- [arXiv:2511.12376v2] BitSnap。动态适配训练阶段与模型结构的稀疏化 + 量化；bitmask 稀疏化在多种规模 LLM 上声称达到 16x 压缩比且不损害模型精度。局限：有损，压缩/解压引入 CPU 开销，集群级结果在摘要中被截断。
- [arXiv:2406.11257v1] ExCP。先计算相邻检查点残差得到稀疏的必要信息，再用 weight-momentum 联合收缩同时利用模型与 momentum 的冗余，声称接近无损。摘要未给出压缩比数字。局限：残差链式依赖使随机访问恢复困难，需完整链条才能重建。
- [arXiv:2602.22158v1] LLMTailor / [arXiv:2609.27193v1] LayerCheck。共同观察是层间更新高度不均匀：前者提供跨检查点按层筛选与组装的合并框架（fine-grained control over weights 与 optimizer states），后者用于 post-training，按阈值只持久化更新超阈值的层。两者摘要均未给出量化收益。局限：阈值选择决定可恢复性上界；跨检查点组装本身要读多个检查点。
- [arXiv:2412.15411v5] MoEvement / [arXiv:2408.04307v3] MoC-System。前者面向 MoE 的分布式内存检查点，三机制为跨迭代增量子集专家快照、稀疏到稠密检查点转换、激活的上游日志；后者提出 Partial Experts Checkpointing，算法-系统协同只保存选定专家子集，把 MoE 检查点压到接近稠密模型量级。摘要均在结论处截断。局限：只对 MoE 结构成立，专家路由漂移时稀疏采样可能漏掉热点专家。
- [arXiv:2509.04084v5] 提出复用训练中已产生的梯度构造差分检查点，理由是梯度尺寸小于差分本身，从而把差分检查点从推荐系统推广到通用分布式训练。

共同假设：未写部分可由梯度/momentum/其他层重建，且重建误差不影响收敛。失效场景：学习率 warmup 或阶段切换（SFT→RL）时更新分布突变，阈值型策略会漏掉关键层；有损压缩与"精确回滚/可复现"要求冲突。

### 2.3 去检查点化：零 I/O 与状态直迁

核心思想：既然写存储是瓶颈，就不写。故障时设备内存往往仍完好，缺的只是框架内部状态（通信句柄、进程组）的可重建性。

- [arXiv:2609.18178v2] AccelPact。面向分片训练的零 I/O 内存内恢复运行时。观察是：通信在已提交的 optimizer step 失败时，设备内存静止且未损坏，继续训练失败是因为 PyTorch FSDP 在 module wrapper 间缓存了通信句柄；于是做动态的框架依赖重绑定。动机数据即第 1 节的 +656.7% / 32.5 GiB / 3.39 TB/hour。局限：只覆盖瞬态通信故障，不覆盖节点永久丢失或内存损坏。
- [arXiv:2607.04749v1] ETC。checkpoint-free 的弹性状态迁移：利用状态局部性最小化跨 GPU 数据移动，用 P2P 直传替代"先落存储再恢复"，并消除节点碎片。摘要截断，无量化。
- [arXiv:2605.18815v1] DynaTrain。提出 Virtual Parameter Space，把所有分布式训练状态统一到一个逻辑坐标空间，使任意并行配置成为确定性映射，从而支持亚秒级在线重配置；配合 rank-local 传输与无死锁调度。这实际上把检查点降级为坐标系变换。
- [arXiv:2412.12636v3] TrainMover。用弹性与 standby 机器处理中断：两阶段 delta 通信组建立、无通信的沙箱预热、通用 standby 支持任意角色恢复；在 1024 GPU 规模声称约 20 秒停机，相比最佳替代方案减少 55% 浪费的 GPU hours（摘要中 "1.4 mi…" 被截断）。

共同假设：故障瞬态、内存状态可信、有可接管的算力。失效场景：静默数据损坏（SDC）与永久性节点损失仍需持久层兜底；无备用容量时退化为等待。

### 2.4 网络与集合通信层：把故障挡在存储之前

核心思想：很多"训练失败"实际是网络瞬断触发 gang scheduling 全作业回滚；若在集合通信层做 failover，就不必产生检查点 I/O。

- [arXiv:2512.11094v2] SHIFT。探索把 RDMA 容错扩展到跨 NIC 级，把流量切到机内备份 NIC。论文首次给出一个 Trilemma：跨 NIC RDMA failover 无法同时满足 Exactly-Once Execution、Receiver-NIC Opacity 与 Zero-Copy datapath。破解点是观察到 NCCL 等框架依赖幂等批量传输、可容忍宽松内存序，只要通知顺序保持。
- [arXiv:2505.14065v1] PCCL。面向公网的容错集合通信库，支持 peer 动态加入与故障恢复，在 all-reduce 进行中仍可继续；强调确定性状态推进使重复操作可行。
- [arXiv:2412.01152v1] INTELLECT-1 / PRIME。跨 3 大洲、最多 14 个并发节点、30 个独立算力提供方动态加入退出，训练 10B 模型 1T token，声称维持 83–96% 计算利用率与 36.2–41.4% 模型 FLOPS 利用率；核心是 ElasticDeviceMesh 管理动态全局进程组。
- [arXiv:2505.12815v2] Chaos。多方可信域外训练，用多邻居状态复制 + 模型分片加速 autoscaling，把分片分配建成 MINLP 再约化为 MILP，导出多项式时间贪心。

共同假设：存在可切换的冗余路径或副本，且复制流量不与训练争抢。失效场景：区域性故障、交换机级故障；复制本身可能成为新的存储与网络开销来源。

### 2.5 重叠与流水线化：把写藏进计算

核心思想：不减少写入量，而是把检查点传输切碎、摊到多个训练步，使其落在通信/CPU 空隙里。

- [arXiv:2511.07035v1] GoCkpt。把检查点分多步传输，每步传一部分状态，并传输用于参数更新的部分梯度数据；传完后把各分片更新为一致状态，最终在 CPU 上恢复。摘要截断，未给出吞吐提升数字。
- [arXiv:2512.03644v1] FFTrainer。利用剩余网络带宽快速存取状态以避免回滚，声称恢复时间最多降低 98%、GPU 利用率损失最多缓解 68%，且不影响正常训练。
- 反例参照：AccelPact 的测量说明"异步检查点"并不免费——在 1.216B 规模上每步异步检查点仍有 +656.7% 延迟 [arXiv:2609.18178v2]。

共同假设：网络/CPU 有可榨取的余量、单步时间足够长可摊销。失效场景：小模型短步长、东西向网络已饱和、检查点尺寸超出单步可隐藏窗口。

### 2.6 评测：没有普适最优

- [arXiv:2610.07688v1] FailBench。统一评测 7 种分布式训练架构、8 种 crash 容错机制加一个无容错基线，覆盖单点、并发与级联 fail-stop；在 8xV100 上跑 142 个（架构, 机制, trace）组合，单 rank 检查点 205 MB–2.7 GB。三条结论：没有机制普遍最优；在 A2 架构上磁盘检查点稳态开销最低（0.5%），内存复制恢复最快（约 17 ms），just-in-time 检查点可避免周期性稳态开销（摘要在此截断）。
- [arXiv:2012.00825v2] 早期 HPC 视角横评。在 Chainer/PyTorch/TensorFlow 上评估检查点计算代价、文件格式与大小、规模影响与确定性检查点，暴露了当时实现的多个瓶颈。价值在于提醒：格式与确定性本身就是一等设计变量。

## 3. 2025–2026 最新进展

1) 目标从"降低检查点开销"转为"取消检查点"：AccelPact 的零 I/O 恢复、ETC 的 checkpoint-free 迁移、DynaTrain 的坐标变换，都把持久层移出关键路径。
2) 恢复语义从"重启作业"转为"不终止作业"：PHOENIX 的 hot-swap、TrainMover 的 standby、LUMEN 的 serving 协调，把 MTTR 目标压向秒级。
3) 存储层次从"远端对象存储"扩展到"本地/对等内存"：TierCheck 的三层与 MoEvement 的内存稀疏快照，说明内存已成为一等检查点介质。
4) 失效模型扩展：TierCheck 的异构故障谱、SHIFT 的跨 NIC Trilemma、FailBench 的级联故障，打破了"crash-stop + 独立故障"的旧假设。
5) 检查点从"容错原语"变成"一等数据对象"：选择（UGCS [arXiv:2511.09864v1]、[arXiv:2510.04848v1]、[arXiv:2604.01025v1]）、合并（[arXiv:2403.19390v2]、[arXiv:2504.18580v1]、Trajectory Soup [arXiv:2609.37169v1]）、安全审计（[arXiv:2610.07518v1] 声称 checkpoint-update 空间的坐标与有害目标组成的 Spearman 相关达 0.986–0.992）、乃至电网调度（[arXiv:2609.26365v1] 指出周期性检查点会造成功率骤降与反弹）都在消费同一份数据。
6) 弹性训练与存储解耦：ERNIE 5.0 [arXiv:2602.04705v1] 在单次预训练内学习一族不同深度/专家容量/路由稀疏度的子模型；EasyScale [arXiv:2208.14228v3] 强调弹性下的精度一致性。

## 5. 对存储系统设计的启示

1. **检查点格式按 base/delta 分层可寻址。** manifest 以 (layer_id, expert_id, step, dtype, codec, checksum, base_ref) 为键，支持按层/按专家独立读取与组装。LayerCheck、LLMTailor、MoC-System 都要求这种粒度；否则选择性持久化省下的写，会被恢复时的全量读抵消。
2. **放置 API 以故障域为第一参数。** 暴露 failure_domain(node/rack/region) × tier(local_mem/peer_mem/remote) 两维，由系统按"该层能承受哪类故障"求解，而不是按容量贪心——这是 TierCheck 三层设计可复用的抽象。
3. **为"零 I/O 恢复"预留旁路接口。** 状态直迁需要 P2P/RDMA 通道与幂等语义；结合 SHIFT 的观察，传输层应提供"可重放的幂等批量写 + 通知顺序保证"，而不是只暴露 read/write。
4. **有损压缩必须自带可验证的重建契约。** 16x 压缩（BitSnap）只有在元数据记录每张量误差界与重建配方、并在加载时校验后，才可安全用于回滚；否则一次静默重建偏差会污染后续所有 step。
5. **检查点生命周期需要 lineage DAG 与引用计数。** 当选择、合并、审计共享同一批对象时，朴素的 LRU 或按步数 GC 会误删仍被合并/审计引用的中间态；应以不可变对象 + 引用计数 + 血缘边管理。
6. **写入窗口需与调度器、电网协同。** 既然周期性检查点会造成功率骤降与反弹 [arXiv:2609.26365v1]，存储侧应支持功率感知的检查点门控；[arXiv:2610.13047v1] 在 2048 GPU、两个 LLaMA 预训练任务上声称 checkpoint-aware 三维调度降低运行成本 20.02%、把弃风从 1.077 降到 0.014（单位在摘要中被截断）。

## 6. 必读五篇

1. TierCheck [arXiv:2605.17821v1] —— 把"故障异构性"变成"分层放置"的范式，定义了本方向的问题空间。
2. AccelPact [arXiv:2609.18178v2] —— 唯一给出存储背压硬数字（+656.7%、32.5 GiB、3.39 TB/hour）并主张零 I/O 的工作。
3. BitSnap [arXiv:2511.12376v2] —— 压缩路线的锚点，16x 是其声称的上界。
4. PHOENIX [arXiv:2607.01646v2] —— "不终止作业"的热替换目标函数，代表 MTTR 导向的设计。
5. FailBench [arXiv:2610.07688v1] —— 目前唯一跨架构/跨机制的对照评测，直接告诉你"没有普适最优"。
