# 分析框架：用"四元组"统一理解存储服务大模型

> 这是本报告的原创分析框架，用于把看似分散的十几个子方向（KV 缓存、checkpoint、向量库、Agent 记忆、模型分发）放到同一张概念地图上。它不是文献综述，而是我们用来提出研究方案的工具。

---

## 1. 为什么需要新框架

现有综述通常按"技术手段"分类：缓存、压缩、卸载、调度、索引。这种分类的缺点是：

- 它把**不同生命周期的数据**混在一起谈。例如"KV cache 压缩"与"模型权重量化"都被称为"压缩"，但前者的对象活几毫秒，后者活几个月，设计约束完全不同。
- 它无法解释**跨层冲突**。例如为什么"前缀缓存要求字节级确定性"会与"稀疏注意力允许丢 token"冲突。
- 它无法预测**下一个瓶颈**。按手段分类只能总结过去，不能指出空白。

我们提出一个以**数据对象**为中心的四元组框架：

$$
\text{StorageObject} = \langle \text{Lifetime},\ \text{ReuseDistance},\ \text{Reconstructibility},\ \text{ConsistencyContract} \rangle
$$

任何大模型产生的数据——训练样本、模型权重、KV 块、向量索引、Agent 记忆、checkpoint——都可以用这四个维度定位。定位之后，存储系统的设计选择（放哪层、怎么索引、要不要复制、如何失效）几乎是**被推导出来的**，而不是拍脑袋的。

---

## 2. 四个维度

### 2.1 生命周期（Lifetime）

数据从产生到不再被需要的时间尺度。

| 量级 | 典型对象 | 存储含义 |
|---|---|---|
| ns–µs | 寄存器、shared memory 中的 tile | 不属于存储系统 |
| µs–ms | 单步 decode 的活跃 KV | 必须在 HBM；任何换出都直接增加 TPOT |
| s–min | 单请求的完整 KV、prefill 结果 | HBM/DRAM；可被调度器换出 |
| min–h | 会话 KV、Agent 工作记忆 | DRAM/SSD；需要 TTL 与复用预测 |
| h–day | 批处理中间态、RAG 文档 KV | SSD/远端池；需要持久化与去重 |
| day–month | checkpoint、数据集分片 | 并行 FS/对象存储；需要版本与 GC |
| month–year | 模型权重、向量索引、合规数据 | 对象存储/冷存储；需要不可变性与审计 |

**关键洞察**：生命周期跨越 **10–12 个数量级**。任何"一刀切"的存储架构都会在某一端失效。这也是为什么"一套存储服务大模型"如此困难——它不是一个大问题，而是七个时间尺度不同的问题被同一个组织同时提出。

### 2.2 复用距离（Reuse Distance）

同一个数据对象被再次访问之前，中间发生了多少次其他访问。存储系统真正关心的是**跨请求/跨会话/跨模型/跨集群**的复用。

| 复用类型 | 例子 | 命中率决定因素 | 正确性风险 |
|---|---|---|---|
| 无复用 | 一次性 batch 推理 | 无 | 无 |
| 同请求内 | decode 逐步读历史 KV | 序列长度 | 无 |
| 跨请求（严格前缀） | system prompt、few-shot | 前缀重合度 | 低（字节相同） |
| 跨请求（非前缀） | RAG 文档块、代码片段 | 文档热度、位置 | **高**（注意力上下文不同） |
| 跨会话 | 多轮对话、Agent 记忆 | 用户回访率 | 中（需版本/隔离） |
| 跨模型 | 同家族不同尺寸、LoRA 变体 | 架构/权重相似度 | **很高**（KV 不可直接迁移） |
| 跨集群/跨地域 | 全局缓存、灾备 | 地理分布 | 高（一致性/合规） |

**关键洞察**：复用距离越远，**正确性问题越重要，而性能收益越不确定**。2023–2024 年的前缀缓存研究集中在"严格前缀 + 字节相同"，所以正确性被隐藏了；2025–2026 年的非前缀/跨上下文复用把这个洞撕开了——SAFE-KV 等工作的测量显示，朴素非前缀复用的答案保真度可以低到 37–47%。

### 2.3 可重建性（Reconstructibility）

数据丢失或未命中时，能否以可接受的代价重新生成。

| 等级 | 定义 | 例子 | 存储策略 |
|---|---|---|---|
| R0 不可重建 | 丢了就永久丢失 | 用户输入、Agent 记忆、标注数据 | 必须持久化 + 复制 + 备份 |
| R1 可重算但昂贵 | 能从原始输入重新计算 | prefill KV、embedding | 缓存；按"重算 vs 读取"经济性决策 |
| R2 可重算且便宜 | 计算代价低 | 简单特征、临时索引 | 可不持久化 |
| R3 可近似重建 | 能重建近似版本 | 量化 KV、草图、摘要 | 需误差界与校验 |

**关键洞察**：**可重建性决定了"缓存"与"存储"的边界**。R1 对象适合缓存（丢了再算），R0 对象必须是存储（丢了就完蛋）。很多系统把 R0 对象（Agent 记忆、用户上传文档）当成 R1 缓存来设计，这是当前 Agent 记忆系统最大的架构错误。

### 2.4 一致性契约（Consistency Contract）

多个读者/写者看到的数据版本之间，允许什么程度的差异。

| 契约 | 含义 | 适用 | 失效后果 |
|---|---|---|---|
| Exact | 字节级相同 | 严格前缀 KV、模型权重 | 命中但错误（静默） |
| Bounded-error | 与全量计算的输出差异 ≤ ε | 量化 KV、稀疏 KV、非前缀复用 | 质量下降，需监控 |
| Snapshot | 某一时刻的一致视图 | checkpoint、数据集版本 | 恢复后不一致 |
| Eventual | 最终一致 | 跨地域缓存、向量索引副本 | 短期脏读 |
| Immutable | 永不修改，只追加 | 模型权重、审计日志、合规数据 | 无法删除（GDPR 冲突） |

**关键洞察**：**当前系统几乎都没有显式声明自己的一致性契约**。前缀缓存的 key 通常只是 token 序列的哈希，不含模型版本、tokenizer、LoRA adapter、量化配置、RoPE scaling——一旦这些变化，缓存会"命中但错误"，而且**不会报错**。这是生产环境最危险的静默故障之一。

## 3. 四元组如何解释现有系统

| 系统/技术 | Lifetime | ReuseDistance | Reconstructibility | Consistency | 被推导出的设计 |
|---|---|---|---|---|---|
| PagedAttention | ms–min | 同请求 | R1 | Exact | 分页、块表、按需分配 |
| 前缀缓存（vLLM/SGLang） | min–h | 跨请求严格前缀 | R1 | Exact（但 key 不完整） | Radix tree / 哈希链 |
| Mooncake | min–h | 跨请求 + 跨实例 | R1 | Exact | 全局 KV 池 + 调度 |
| LMCache | min–day | 跨请求/跨引擎 | R1 | Exact | 分层后端 + 统一接口 |
| InfiniGen / ShadowKV | ms | 同请求 | R1 | Bounded-error | 稀疏索引 + 预取 |
| KV 量化（KIVI） | ms | 同请求 | R3 | Bounded-error | 低比特 + 反量化 |
| 非前缀复用（CacheBlend/SAFE-KV） | min | 跨请求非前缀 | R1/R3 | Bounded-error | 选择性重算 + 修复 |
| Checkpoint | day–month | 跨作业/跨集群 | R0（训练状态） | Snapshot | 分片 + manifest + 原子提交 |
| 向量索引（DiskANN） | day–month | 跨请求 | R2（可从原文重建） | Eventual | SSD 图 + 内存导航 |
| Agent 记忆（Mem0/Zep） | month–year | 跨会话 | R0 | 应为 Transactional | 目前多为最终一致，缺口 |
| 模型权重（safetensors/Xet） | month–year | 跨模型/跨集群 | R0 | Immutable | 内容寻址 + CDC 去重 |

这张表本身就是报告的"技术地图"：**同一行内的技术选择，几乎都可以由前四列推导出来**。

## 4. 三个"时钟"的错位

存储系统同时被三个不同速度的时钟驱动：

1. **计算时钟**（ns–µs）：GPU 周期、kernel launch、HBM 访问。
2. **数据时钟**（ms–h）：KV 生成与消费、请求到达、会话生命周期。
3. **治理时钟**（day–year）：模型版本、数据合规、计费、审计、GC。

**大多数系统故障不是性能问题，而是时钟错位**：

- KV 缓存按毫秒淘汰，但合规要求"用户删除后 30 天内清除所有衍生数据"——KV 是衍生数据，谁负责删？
- 模型每周更新，但缓存 key 不含模型版本——旧 KV 被新模型命中。
- 计费按 token，但缓存命中省下的算力没有计入成本模型——缓存的经济性无法归因。
- checkpoint 每 5 分钟写一次，但审计要求保留 90 天——累计 167 PB 的写入与保留策略冲突。

**研究机会**：把"治理时钟"纳入存储系统的第一类设计对象，而不是事后补丁。这正是我们提出"KV 对象存储 + 复用契约"和"事务型 Agent 记忆"两个方案的出发点。

## 5. 四面"墙"

大模型的存储问题可以分解为四面墙，每面墙对应不同的技术路线：

| 墙 | 定义 | 当前状态 | 主要对策 | 代表工作 |
|---|---|---|---|---|
| **容量墙** | KV/权重/checkpoint 总量超过可用介质 | 70B/128K/batch32 ≈ 1.25 TiB KV | 分层、压缩、复用、CXL | Mooncake、LMCache、KIVI、CXL 池化 |
| **带宽墙** | decode 每 token 需读全部历史 KV，算术强度仅 2r/b | GQA-8/FP16 = 8 FLOP/B，远低于 H100 拐点 295 | 稀疏化、量化、近存计算、GQA/MLA | InfiniGen、Quest、KIVI、DeepSeek MLA |
| **元数据墙** | 小对象/前缀索引/租约的 ops 压力 | 百万级 prefix 块、千万级向量 | 哈希链、Radix、事务型 KV、批量 | vLLM APC、SGLang、3FS FoundationDB |
| **寿命墙** | SSD 写放大与 TBW 消耗 | KV 写入量可在数月内耗尽 SSD 寿命 | 写入门控、ZNS、寿命感知放置 | Gandalf (2026)、CXL-SSD |

**关键洞察**：四面墙不是独立的。压缩降低容量墙，但可能增加带宽墙（解压算力）和寿命墙（写放大）；分层缓解容量墙，但增加元数据墙和带宽墙。**任何方案都必须同时报告它对四面墙的影响**，否则就是"把问题搬到下一层"。

## 6. "复用三角"：命中率 × 正确性 × 成本

任何 KV/语义复用方案都在这三个维度上取点：

```
        正确性
          /\
         /  \
        /    \
       /      \
      /________\
  命中率      成本
```

- **严格前缀缓存**：正确性最高（字节相同）、成本最低，但命中率受限于前缀重合。
- **非前缀/语义复用**：命中率提高，但正确性下降，需要修复/校验成本。
- **全量重算**：正确性最高，但成本最高、命中率概念消失。

2026 年的研究前沿正是**把"正确性"从隐含假设变成显式可调参数**：SAFE-KV 用因果后缀修复把保真度从 47% 提到 99%；KVBoost 用 deviation-guided recomputation；KV-Repurpose 提供评测 testbed。但**存储层还没有对应的抽象**——没有 API 让上层说"我接受 ε=0.01 的误差，请给我最便宜的 KV 版本"。

这就是本报告研究方案 P1/P4 的核心机会。

## 7. 框架的预测能力

一个好的框架应该能预测"哪里会有下一个问题"。用四元组推演：

1. **Agent 记忆**：R0 + 跨会话 + 多写者 + 治理时钟 → 必然需要事务、MVCC、溯源、加密删除。当前系统把它们当向量库，所以下一波问题一定出在**一致性、删除传播、投毒**。
2. **跨模型 KV 复用**：R1 但一致性契约是"模型相关" → 需要把模型指纹纳入 key；否则 2026–2027 会出现一批"缓存命中但输出漂移"的静默故障。
3. **长上下文 + 多租户**：容量墙 + 元数据墙 + 隔离 → 需要"租户感知的 KV 分区 + 公平淘汰"，而不是全局 LRU。
4. **视频/世界模型**：生命周期长、体积大、可重建性低 → 存储会成为训练瓶颈，且需要时序索引，而不是 KV 式缓存。
5. **合规删除**：R0 + 多副本 + 衍生 KV → 需要"删除传播协议"，这将是存储系统的新一等功能。

这些预测直接转化为第四部分的研究方案。
