## 执行摘要

**一句话判断**：存储已经是大模型系统的第一性约束，但当前产业与学术界对它的理解仍停留在"容量不够就 offload"。2025–2026 年的真实进展表明，真正的瓶颈已经转移到三个更棘手的问题上：**搬得动吗（对象粒度与路径）、搬得对吗（复用保真度）、搬得起吗（SSD 寿命与 TCO）**。

**五个最重要的结论**：

1. **KV 不是"大一点的数据"，而是一类新的存储对象**。它的体积由注意力结构决定（$2Ldb/r$），与参数量无直接关系；70B/128K/batch32 的 KV 约 1.25 TiB，已经超过多数单机内存。
2. **Decode 在物理上就是带宽受限**。GQA-8/FP16 的算术强度上界是 8 FLOP/B，比 H100 的 roofline 拐点低 37 倍；增大 batch 只能把"权重受限"变成"KV 受限"，不能变成 compute-bound。
3. **2026 年最大的认知更新是"命中不等于可用"**。非前缀复用的朴素拼接只能保留 37.8%–47.2% 的全量 prefill 答案；修复后可回到 98%–99.8%。复用正确性必须成为存储系统的一等契约。
4. **SSD 的角色被高估也被低估**：它不能做 decode 的逐 token 数据源（带宽差 4× 以上），但正在成为 prefill 复用与冷容量的主层；与此同时，KV 写入量可在数月内耗尽 SSD 寿命，写策略成为设计中心。
5. **训练侧的存储主角是 checkpoint，不是数据加载**。LLM 训练的数据流只有 12–50 MB/s（1024 GPU 聚合），但 checkpoint 的 bytes/FLOP 比数据加载高 10³–10⁵ 倍，峰均比可达 77×。

**给不同读者的建议**（详见第 6 节）：

- **模型公司/推理平台**：把 KV 当对象存储来建（命名、版本、复用契约、寿命预算），而不是当缓存来调 LRU。
- **云厂商**：多租户隔离与缓存侧信道已到"能不能上线"的程度；优先建 KV 存储的可观测性与基准。
- **存储厂商**：接口正从"路径"退化为"可 RDMA 注册的 buffer + 完成描述符"；竞争焦点从带宽转向 KV namespace 与数据编排。
- **研究者**：最高优先级是 KV 复用契约、SSD 寿命感知的写入门控、KV 存储基准（见 `04`）。

## 1. 五个结构性事实（先建立数量级直觉）

完整的公式与算例见 `raw/analysis-quant.md`。这里只保留决策所需的结论。

### 1.1 KV 体积：架构决定，不是参数量决定

| 模型（代表配置） | 每 token KV | 128K 单请求 | 128K × batch 32 |
|---|---:|---:|---:|
| 7B-GQA | 128 KiB | 16 GiB | 0.50 TiB |
| 70B（GQA-8） | 320 KiB | 40 GiB | 1.25 TiB |
| 405B（GQA-16） | 504 KiB | 63 GiB | 1.97 TiB |
| 671B MoE + MLA | 68.6 KiB | 8.6 GiB | 0.27 TiB |

**决策含义**：不能用"参数量 × 常数"做容量规划；MoE + MLA 可以让 671B 的 KV 小于 405B dense 7 倍。采购与调度系统必须读取注意力配置。

### 1.2 Decode 的带宽墙

$I_{\text{dec}}^\infty = 2r/b$。GQA-8/FP16 = 8 FLOP/B；H100 拐点约 295 FLOP/B。**结论**：长上下文 decode 在任何 batch 下都是 memory-bound。增大 batch 改善的是吞吐，不是算术强度；真正的杠杆是 GQA/MLA（架构）与低精度（$b$）。

### 1.3 Prefill vs Decode：3–4 个数量级的差异

32K 上下文的 prefill 算术强度约 $3\times10^4$ FLOP/B（compute-bound），decode 约 8 FLOP/B（memory-bound）。这不是工程偏好，而是 PD 分离的物理基础。

### 1.4 Checkpoint：8 倍权重、77 倍峰均比

Adam 状态约 16 B/param：70B = 1.12 TB，671B = 10.7 TB。最优间隔 $\tau^*=\sqrt{2\delta M}$ 是分钟级；671B 在 3.6 s 写完时峰值约 3 TB/s，平均 39 GB/s。**按平均带宽采购会低估两个数量级。**

### 1.5 成本：存下来 vs 重算，临界点由"保留时长 × 复用次数"决定

70B 每百万 token 重算约 \$0.25（线性项）；KV 存 SSD 30 天约 \$33，存 DRAM 30 天约 \$983。盈亏平衡复用次数：SSD-30d 约 14 次，DRAM-30d 约 387 次，SSD-1h 约 1 次。

**最容易被忽略的**：对象存储的 egress 会让跨域读取一次 1M token 的 KV 比重算贵 2–13 倍。**"把 KV 沉到 S3 做全局缓存"在公有云上通常不成立**，除非读写同 region 且 egress 免费，或读取被上百次复用摊薄。

## 2. 十大发现（2025–2026 的真实进展）

> 每条发现都给出证据与"它对设计意味着什么"。引用均可在 `05` 中按 ID 查到。

### 发现 1：决定 TTFT 的是"对象数"，不是"字节数"

**证据**：Range [arXiv:2610.21241] 测得同样 6 GiB KV，切成 192 个对象恢复需 2.1 s，切成 6,144 个对象需 3.0 s；查找、分配、提交 I/O、送 GPU、写回、索引**每一层都按对象计费**。Tutti [arXiv:2605.03375] 进一步指出 GPU 显存碎片会产生海量微小随机 I/O，即使启用 GDS，CPU 仍要为每次 I/O 介入；ContiguousKV [arXiv:2601.13631] 则指出语义级细粒度选 token 与粗粒度定长 I/O 块不匹配，直接变成读放大。

**设计含义**：存储系统需要暴露**批量/聚合 I/O**（一个描述符搬多个块），而不是让上层循环发 4 KiB 读。KV 的逻辑粒度（token/层/头）与物理粒度（4 KiB 页/对象）必须显式对齐。

### 发现 2："远端命中一定更快"不再成立

**证据**：在 GLM-5.3（FP8 MoE + MLA）的 8×B300 上开启远端层，中位 TTFT 不变，但 16k token 的 **p99 从 3.96 s 涨到 17.3 s**；一次远端命中耗时 **0.88 s**，而重算 prompt 只要 **0.31 s**；同步加载把命中密集的流变成不稳定队列，p99 达 83.32 s 而 GPU 只有 7% 忙 [arXiv:2610.21500]。

**设计含义**：缓存策略必须是**在线代价决策**（fetch vs recompute），而不是静态分层。需要把 GPU/网络/SSD 争用、SLO deadline 纳入同一控制器，并支持"取算对冲"（先完成者胜出）。

### 发现 3：SSD 寿命从脚注变成一等约束

**证据**：多轮对话与 agent 负载下，KV 累计写入量显著超过 SSD 容量，寿命从"数年"缩短到"数月" [arXiv:2610.30791]；急切持久化所有块会迅速耗尽耐久度，而 GPU 服务器上 SSD 数量有限又限制重载带宽 [arXiv:2610.31169]；HBF 场景发现 LRU 把写入与 miss 耦合，产生过量写流量 [arXiv:2609.07175]。反过来，前缀感知去重的写量削减只对 exact-repeat（同上下文、同 prompt）负载显著，该组写入从 1.62 GB 降到 11.75 MB，其余三类负载写量仍在 2–5 GB；而“几乎不读 SSD”只是 legacy 栈在页缓存温热时的假象——一旦缓存被逐出，同一路径在 683 ms 内发出约 1 GB 顺序读 [arXiv:2610.21249]。

**设计含义**：KV 存储需要 **TBW 预算与写入门控**，把"写多少"与"命中率"联合优化；ZNS、OP 预留、冷热分离应进入设计空间。**只看 \$/GB 的 TCO 模型会系统性低估 KV 落盘成本。**

### 发现 4：复用的核心问题是正确性，不是命中率

**证据**：SAFE-KV [arXiv:2610.15186] 报告，前缀条件下拼接只保留 HotpotQA-500 的 **47.2%**、2Wiki-500 的 **37.8%** 全量 prefill 答案；风险引导修复后回到 **99.8%/98.4%**。更根本的是"tolerable set" [arXiv:2610.22016]：冻结的 transformer 只能读取接近"它自己会写出"的缓存，几何相似度不能预测读者能否使用，且失败不是渐进的。5% 重算预算下，文档对齐重算把跨请求顺序的答案波动从 69.0% 降到 26.1% [arXiv:2610.05833]。

**设计含义**：需要 **KV 复用契约**——在元数据里记录来源、版本、误差界，并提供 `can_reuse(query, epsilon)` 之类的 API；存储层要能返回"精确 / 有界误差 / 需重算"三档，而不是布尔命中。

### 发现 5：CXL 不是万能解，现货性能普遍不达预期

**证据**：CXL-SSD 比本地 DRAM 慢约 **3×**，且并不比 NVMe SSD 更快，通用预取几乎无收益 [arXiv:2609.26828]；CXL 链路与设备侧 DDR 带宽远低于 HBM，必须靠压缩才能维持解码 [arXiv:2509.03377]；光子 CXL 用无源光纤 shuffle 在 16 主机间提供 32 TB 共享内存，相对电气 CXL 池延迟降低逾 50%（emulation）[arXiv:2607.27187]。

**设计含义**：CXL 的价值在**容量扩展与共享**，不在替代 HBM 带宽。要用好它，必须把 KV chunk 语义下沉到设备（claim/commit、设备可见 I/O 单元），并做布局感知的压缩；否则只是"更远的 DRAM"。

### 发现 6：GPU 开始直控 I/O，但"对象粒度税"仍在

**证据**：Tutti 把 KV 做成 GPU 侧对象存储，CPU 只负责异步控制 [arXiv:2605.03375]；DUAL-BLADE 按运行时空闲内存动态分配 page-cache 路径与 NVMe-direct 路径，后者把 KV 映射到连续 LBA、绕过文件系统 [arXiv:2604.26557]；DAK 复用 TMA 把远端内存中的权重与 KV 直接搬入 SMEM [arXiv:2604.26074]。但 Range 的结论是必要的冷水：把每对象工作从 CPU 移到 GPU，**工作本身仍然是每对象的** [arXiv:2610.21241]。

**设计含义**：GPU-initiated I/O 是确定的趋势，但必须同时解决对象聚合、QoS 隔离与错误处理；否则只是把 CPU 瓶颈换成 GPU 瓶颈。

### 发现 7：模型架构正在让"前缀缓存"这一抽象失效

**证据**：全注意力 KV 可按 token 寻址，而线性注意力层维护的 recurrent state 无法回滚到任意前缀边界，现有系统只能物化检查点，把复用限制在离散边界 [arXiv:2609.33477]；Tail-Replay 把 Gated DeltaNet 视作对前缀的结构化有损压缩 [arXiv:2608.30310]；HiState 面向 agent 负载管理分层检查点 [arXiv:2610.41508]。调度层也出现"匹配到前缀但状态未就绪"的执行气泡 [arXiv:2610.18143]。

**设计含义**：存储抽象必须从"token 可寻址的 KV 数组"扩展到"**可检查点化的模型状态**"；混合注意力/线性注意力需要新的状态快照与回滚协议。

### 发现 8：Checkpoint 正从"文件"变成"可重分片数据集"，并出现零 I/O 恢复

**证据**：TierCheck 用本地/对等内存 + 远端持久层三层设计，按故障域放置 [arXiv:2605.17821]；AccelPact 用零 I/O 内存内恢复，动机数据是每步异步检查点仍带来 **+656.7%** 延迟、32.5 GiB 主机内存、3.39 TB/hour 流量 [arXiv:2609.18178]；PHOENIX 用 hot-swap 避免终止作业 [arXiv:2607.01646]；FailBench 横评 142 个组合后结论是"**没有机制普遍最优**"；在 A2 架构上，磁盘检查点稳态开销最低（0.5%），内存复制恢复最快（约 17 ms）[arXiv:2610.07688]。

**设计含义**：checkpoint 需要 **manifest + 内容寻址 + 增量 + 原子提交 + 按故障域放置**；"异步"不是免费的，必须把 CPU/内存/网络开销计入。存储系统应提供 durability class 与 RPO/RTO 契约。

### 发现 9：Agent 记忆是 R0 数据，却被当成缓存设计

**证据**：GEM 把记忆正确性定义为"状态轨迹"而非单条记录，提出 ingest/revise/forget/retrieve 四算子与六条正确性条件 [arXiv:2605.26252]；ChronoMem 每次写入提交整库快照并支持自然语言回滚 [arXiv:2607.27773]；Bemula 把遗忘变成一等评测（50 段对话、135 条遗忘请求、1742 个问题）[arXiv:2610.18052]；安全侧，记忆库对 84.7% 的必需应用能检出他人凭证，压力测试下 80–94% 的运行会使用他人凭证 [arXiv:2610.25707]。

**设计含义**：Agent 记忆需要 **事务、MVCC、provenance、加密删除、多租户隔离**；把 R0 数据放进最终一致的向量库是架构错误。这是存储社区最明显的机会窗口之一。

### 发现 10：缓存已经成为安全边界

**证据**：多租户共享前缀缓存构成时间侧信道，PROMPTPEEK、EarlyBird、InputSnatch 三类攻击对未防护的 vLLM/SGLang 成功率可达 **100%** [arXiv:2608.09225]；对真实 API 的统计审计在包括 OpenAI 在内的 **七家提供商**中检测到跨用户全局缓存共享 [arXiv:2502.07776]；API 网关层还可能绕过提供商级隔离 [arXiv:2605.30613]；语义缓存面临投毒与键碰撞 [arXiv:2608.01718]。

**设计含义**：前缀共享必须默认带**租户分区/加密/访问控制**；缓存 key 需要包含租户与权限域；计费与审计需要能追溯"谁读了谁的 KV"。多租户隔离不是工程细节，是研究问题。

### 元发现：评测缺失导致"收益"不可比

**证据**：两家公司生产 trace 上 **14 种驱逐算法相对 LRU 提升有限** [arXiv:2609.28870]；20 种混合负载下没有单一最优策略，LRU 在 agent 密集场景比 S3FIFO 高 12%，其余场景最多落后 22% [arXiv:2610.36355]；KV 压缩组合在该单设备短上下文实验中未叠加（FP4 + Polar 串联后 4,241 B/token、15.1 tok/s，两个维度都劣于单用 FP4）[arXiv:2610.33076]；FailBench 显示 checkpoint 机制"没有普遍最优" [arXiv:2610.07688]。

**含义**：大量论文的 speedup 来自不同 baseline、不同负载、不同硬件，**跨论文比较没有意义**。领域缺一个 KV 存储基准（见提案 P9）——这本身就是高价值研究。

## 3. 技术族优劣势对比

> 评分是**相对判断**，不是绝对排名。成熟度定义：实验 / 早期采用 / 规模化 / 标准化。

### 3.1 KV 分层与卸载（HBM→DRAM）

**优势**
- 成熟度最高，vLLM/SGLang/TensorRT-LLM 均有原生或插件支持；
- 对多轮对话、长 system prompt 的 TTFT 改善直接且可复现；
- 不改变模型精度。

**劣势**
- DRAM 容量仍受单机通道数限制，无法支撑 TB 级会话；
- 与权重/其他租户争抢带宽，p99 可能恶化；
- 远端层一旦跨节点，延迟与故障域问题立刻出现。

**成熟度**：规模化。**适用**：单机多轮、前缀复用。**不适用**：跨机长上下文、超大规模多租户。

### 3.2 SSD-backed KV

**优势**
- 容量/成本比 DRAM 高一个数量级，可支撑 TB–PB 级 KV 池；
- 与前缀复用结合可显著降低 TTFT（尤其 RAG/多轮）；
- 本地 NVMe + GPU 直控 I/O 的路径正在成熟。

**劣势**
- **带宽不够做 decode 数据源**：70B/128K 每步需约 430 GB/s，单节点 8×Gen5 NVMe 约 100 GB/s；
- **寿命**：KV 写入量可在数月耗尽 TBW；
- 对象粒度税、写放大、GC 抖动、尾延迟。

**成熟度**：早期采用 → 规模化（头部玩家）。**适用**：prefill 复用缓存、冷容量、跨会话。**不适用**：逐 token decode 读。

### 3.3 CXL 内存池 / CXL-SSD

**优势**
- 字节可寻址、免拷贝、可跨节点共享，理论上比 RDMA 池延迟低；
- 适合做"温层"与共享前缀池；
- 光子 CXL 可突破电气交换的距离/功耗限制。

**劣势**
- 现货 CXL-SSD 比 DRAM 慢约 3×、不比 NVMe 快；
- 链路带宽远低于 HBM，压缩/布局变换是必需项；
- 生态、RAS、多租户隔离、软件栈成熟度低。

**成熟度**：实验 → 早期。**适用**：512 GiB 级以上共享池、Engram/稀疏表。**不适用**：高带宽 decode。

### 3.4 对象存储 KV

**优势**
- 容量近乎无限、\$ /GB 最低；
- 适合跨集群、跨地域的冷 KV 与归档；
- 与数据湖/模型仓库天然集成。

**劣势**
- 延迟毫秒–百毫秒级，egress 费用可能比重算更贵；
- 需要协议协同（按消费顺序交付）才能收敛 TTFT；
- 原子性/一致性弱，不适合作为 checkpoint 主存储。

**成熟度**：早期。**适用**：冷 KV、跨域备份、读多写少。**不适用**：在线 decode、频繁更新的会话。

### 3.5 KV 压缩 / 量化 / 稀疏

**优势**
- 直接降低容量与带宽，收益可叠加到所有下层；
- 2-bit 量化、20× 变换编码已可用；
- 与架构级压缩（GQA/MLA）互补。

**劣势**
- 精度损失与任务强相关（检索/多跳最敏感）；
- 压缩/解压消耗算力与带宽，组合不叠加；
- 破坏精确前缀匹配的块对齐，影响复用。

**成熟度**：规模化（有争议）。**适用**：容量受限、可容忍有界误差。**不适用**：高精度推理、需要字节级确定性的复用。

### 3.6 前缀 / 非前缀复用

**优势**
- 对共享 system prompt、RAG、Agent 场景收益最大；
- 不需要改模型，工程可落地；
- 与 KV 池、PD 分离天然协同。

**劣势**
- 严格前缀命中率受负载限制；
- 非前缀复用有正确性风险（保真度可低至 37.8%）；
- cache key 语义复杂（模型/tokenizer/adapter/量化/RoPE）；
- 侧信道与多租户隔离问题。

**成熟度**：前缀=规模化；非前缀=试点。**适用**：RAG、多轮、Agent。**不适用**：无共享内容的一次性请求。

### 3.7 PD 分离与 KV-aware 调度

**优势**
- 从物理上匹配 prefill（compute-bound）与 decode（memory-bound）；
- 显著提升 goodput，已被多家生产验证；
- 与 KV 池、路由结合可进一步提升命中率。

**劣势**
- 收益高度依赖 SLO、模型与负载，跨论文数字不可比（DistServe 的 7.4× 是 TTFT/TPOT 约束下的请求率，Splitwise 的 1.4× 是吞吐/成本口径）；
- 依赖高速 RDMA/NVLink，网络成为新瓶颈；
- 短上下文/低并发场景收益有限；
- 调度器复杂度与故障域增加。

**成熟度**：规模化。**适用**：大规模在线服务。**不适用**：单机小规模、短请求。

### 3.8 向量库 / RAG 存储

**优势**
- 成熟生态（DiskANN/SPANN/Milvus/FAISS）；
- SSD 原生索引可支撑十亿级向量；
- 与 RAG/Agent 记忆天然结合。

**劣势**
- 更新/删除写放大，embedding 版本迁移成本高；
- 过滤检索与多租户支持弱；
- 检索质量与存储成本/延迟的三角权衡。

**成熟度**：规模化。**适用**：知识库、语义检索。**不适用**：强事务、高频更新。

### 3.9 分布式文件系统（训练）

**优势**
- 3FS/vePFS/Lustre 可提供 TB/s 级聚合带宽；
- 元数据与数据分离、RDMA、用户态零拷贝；
- 统一命名空间支持数据/checkpoint/KV 共池。

**劣势**
- 建设与运维成本高；
- 小文件元数据仍是瓶颈；
- 多租户 QoS 与跨地域能力弱；
- 部分系统闭源、缺公开评测。

**成熟度**：规模化。**适用**：千卡–万卡训练。**不适用**：小团队、推理 KV 池（除非复用）。

### 3.10 Checkpoint / 容错

**优势**
- 直接决定 MFU 与作业可靠性；
- 增量/异步/分层/零 I/O 路线丰富；
- 与训练框架解耦的格式（DCP/ByteCheckpoint）已成熟。

**劣势**
- "异步"不等于免费（+656.7% 延迟的实测）；
- 控制面（manifest/GC/跨集群/原子提交）研究不足；
- 有损压缩与精确回滚冲突；
- 恢复读风暴与元数据竞争。

**成熟度**：规模化。**适用**：所有大规模训练。**不适用**：单卡/小规模（成本不划算）。

### 3.11 模型加载 / 分发

**优势**
- 冷启动直接决定 serverless 成本；
- CDC 去重、多播、execute-while-load 可显著降低加载时间；
- safetensors/Xet 已成事实标准。

**劣势**
- 模型变体爆炸导致存储放大；
- 跨变体 KV 复用语义漂移；
- 供应链安全（签名/SBOM）几乎无系统研究；
- 机密计算下 DMA 假设失效（吞吐损失 13–27%）[arXiv:2606.23969]。

**成熟度**：safetensors=标准化；CDC=早期。**适用**：多模型/多租户推理。**不适用**：单模型常驻。

### 3.12 Agent 记忆

**优势**
- 需求真实且增长最快；
- 与向量库/图数据库/文件系统可组合；
- 存储层可提供事务、版本、溯源等成熟能力。

**劣势**
- 现有系统多为最终一致，缺 ACID/隔离；
- 写放大严重（每次历史数百–数千次 LLM 调用）；
- 遗忘/删除传播、投毒、跨用户凭证误用；
- 评测基准碎片化。

**成熟度**：早期。**适用**：长时程 Agent、个人助手。**不适用**：无状态问答。

### 3.13 近存计算 / CSD / PIM

**优势**
- 理论上可消除 PCIe 搬运，适合 attention/检索；
- 在冷数据、稀疏访问场景有数量级潜力。

**劣势**
- 器件算力/散热受限，持续负载会降频；
- 编程模型与厂商接口不统一；
- 全 attention 下沉已被证伪，只适合轻量判定；
- 缺规模化部署证据。

**成熟度**：实验（降温）。**适用**：token 重要性判定、HNSW 内核。**不适用**：精确 attention、热数据。

### 3.14 一张总表

| 技术族 | 核心收益 | 最大风险 | 成熟度 | 最佳场景 |
|---|---|---|---|---|
| HBM→DRAM 卸载 | TTFT、容量 | 带宽争用 | 规模化 | 单机多轮 |
| SSD-backed KV | 容量/成本 | 寿命、带宽 | 早期→规模化 | prefill 复用 |
| CXL 池/CXL-SSD | 共享、免拷贝 | 现货性能不达预期 | 实验→早期 | 大池、稀疏表 |
| 对象存储 KV | 无限容量、低成本 | egress、尾延迟 | 早期 | 冷 KV |
| KV 压缩 | 容量+带宽 | 精度、组合不叠加 | 规模化 | 容量受限 |
| 前缀/非前缀复用 | TTFT | **正确性** | 规模化/试点 | RAG、Agent |
| PD 分离 | goodput | 网络、复杂度 | 规模化 | 大规模在线 |
| 向量库 | 检索 | 更新成本 | 规模化 | 知识库 |
| 分布式 FS | 聚合带宽 | 运维、元数据 | 规模化 | 万卡训练 |
| Checkpoint | MFU、可靠性 | 控制面、异步开销 | 规模化 | 大训练 |
| 模型分发 | 冷启动 | 变体放大、安全 | 标准化/早期 | 多模型 |
| Agent 记忆 | 长期状态 | 一致性、安全 | 早期 | 长时程 Agent |
| CSD/PIM | 消除搬运 | 器件/生态 | 实验 | 轻量判定 |

## 4. 成熟度与产业采用

### 4.1 技术雷达（2026）

> 本节沿用技术雷达档位（已量产 / 早期量产 / 试点 / 原型 / 研究 / 降温）；与 §3 四档的映射：已量产/早期量产 ≈ 规模化/早期采用，试点/原型 ≈ 实验→早期，研究 ≈ 实验。

| 技术 | 成熟度 | 代表工作 | 判断 |
|---|---|---|---|
| SSD KV 卸载 | 规模化（LMCache）/ 原型（KVDrive） | LMCache [arXiv:2510.09665]、KVDrive [arXiv:2605.18071] | 默认方案；下一道坎是寿命。KVDrive 论文仅报告原型，无生产部署证据 |
| GPU 直控 KV 对象存储 | 早期量产 | Tutti [arXiv:2605.03375]、Range [arXiv:2610.21241] | 收益确定，需重写 I/O 路径 |
| 非前缀/段级复用 | 试点 | KVBoost [arXiv:2608.21362]、SAFE-KV [arXiv:2610.15186] | 成败取决于修复成本与正确性度量 |
| CXL 内存池 | 试点 | Beluga [arXiv:2511.20172]、CXL-K8s [arXiv:2609.10790] | K8s 原生 DRA 调度；需 512 GiB 级共享池才划算 |
| CXL-SSD | 原型 | LM-CXD [arXiv:2609.26828]、TempoKV [arXiv:2609.35065] | 现货无优势，必须软硬协同 |
| 光子 CXL | 原型 | [arXiv:2607.27187] | 解决电气 CXL 的距离/功耗 |
| 计算存储 | 降温 | [arXiv:2604.02442]、[arXiv:2602.18750] | 只卸载轻量判定 |
| 混合注意力缓存 | 研究 | [arXiv:2609.33477]、[arXiv:2610.41508] | 架构倒逼存储抽象重写 |
| 跨模型 KV 复用 | 研究 | [arXiv:2512.17910]、[arXiv:2606.07684] | 语义漂移是硬约束 |
| KV 量化/编码 | 量产（有争议） | KVTC [arXiv:2511.01815] | 收益趋同，进入噪声区 |
| Agent 缓存指令/TTL | 试点 | Continuum [arXiv:2511.02230]、Leyline [arXiv:2606.01065] | 需引擎暴露原语 |
| 缓存侧信道防护 | 试点 | KVGov [arXiv:2608.09225] | 多租户合规刚需 |

### 4.2 产业格局：五种路线

| 路线 | 代表 | 核心主张 | 存储观 |
|---|---|---|---|
| 加速器厂商 | NVIDIA、华为 | 存储是"传输描述符 + 内存层级" | 接口下沉到 buffer/descriptor |
| 模型公司 | DeepSeek、Moonshot、字节、Meta | 自建 KV 池 + 高带宽 FS | 存储是核心竞争力 |
| 云厂商 | 阿里、Google、Microsoft | POSIX 性能层 + 对象容量层 + 缓存 | 存储是云服务，TCO 优先 |
| 存储厂商 | WEKA、VAST、DDN、华为 | AI-native FS + KV tier | 卖带宽与多协议 |
| API 厂商 | Anthropic、OpenAI | 缓存/记忆产品化为 API 语义 | 存储是 TTL/定价/命名空间 |

**关键判断**：存储厂商与推理框架正在争夺 **KV namespace** 的定义权。谁定义 KV 的寻址、生命周期与计费，谁掌握下一层话语权。NVIDIA 用 Dynamo/KVBM/NIXL 把 KV 收进推理栈，WEKA 用 Augmented Memory Grid 把它拉进文件系统——这场竞争在 2026 年才刚刚开始。

### 4.3 工业界领先学术界的地方

工业生产中真正难、但论文几乎不写的东西：

1. **cache key 的完整语义**：模型版本、tokenizer、LoRA adapter、量化配置、RoPE scaling 都必须进 key，否则"命中但错误"；
2. **多租户配额与 QoS**：每租户多少 KV、满了淘汰谁、RDMA NIC 跨租户干扰、按 token 计费；
3. **可观测性**：TTFT 分解（排队/预填充/KV 传输/解码）、命中率三种口径、SSD 磨损、静默错误、慢节点定位；
4. **失效协议**：文档更新、模型更新、用户删除如何级联使 KV/索引/记忆失效；
5. **TCO 归因**：SSD 寿命、网络 egress、缓存命中 ROI 的联合核算。

这五点正是研究机会，而不是"工程细节"。

## 5. 九个常见误区

| # | 误区 | 为什么错 | 正确做法 |
|---|---|---|---|
| 1 | "KV 放 SSD 就行" | 带宽差 4× 以上，不能做逐 token 数据源；寿命数月耗尽 | SSD 只做 prefill 复用/冷容量；decode 靠 HBM/DRAM/稀疏化 |
| 2 | "命中率越高越好" | 命中不等于可用；非前缀复用保真度可低至 37.8% | 把保真度/误差界纳入指标；必要时选择性重算 |
| 3 | "压缩比越高越好" | 组合不叠加；精度损失与任务强相关 | 按任务 SLA 选压缩；报告误差界 |
| 4 | "对象存储最便宜" | egress 使一次读取比重算贵 2–13× | 同 region/高复用才用；否则建 RDMA 池 |
| 5 | "异步 checkpoint 免费" | 实测仍有 +656.7% 延迟、3.39 TB/hour | 把 CPU/内存/网络开销计入；用零 I/O/增量 |
| 6 | "LRU 就够了" | 14 种算法相对 LRU 提升有限，但租户公平/recency 同步仍会出事 | LRU + 租户配额 + 会话感知 |
| 7 | "模型越大 KV 越大" | KV 由 L·d/r 决定；671B MLA 比 405B dense 小 7× | 读注意力配置做容量规划 |
| 8 | "CXL 是万能解" | 现货 CXL-SSD 不比 NVMe 快；链路带宽远低于 HBM | 只用于容量/共享；配合压缩与设备语义 |
| 9 | "多租户是工程细节" | 缓存侧信道攻击成功率 100%；七家提供商检出跨用户共享 | 把隔离/配额/审计作为一等需求 |

## 6. 建议

### 6.1 给模型公司 / 推理平台

1. **建 KV 对象存储，而不是 KV 缓存**：命名 `(model_hash, tokenizer, adapter, precision, token_span, rope)`，带版本、来源、误差界；提供 `can_reuse` 而非布尔命中。
2. **做在线 fetch-vs-recompute 决策**：把远端命中 0.88 s vs 重算 0.31 s 这类事实纳入控制器；支持尾延迟对冲。
3. **给 SSD 建 TBW 预算**：把写入门控、ZNS/OP 预留、冷热分离纳入容量规划；用 5 年 TCO 而非 \$/GB。
4. **优先解决对象粒度**：批量描述符、聚合 I/O、KV 逻辑/物理粒度对齐；这比换更快的 SSD 更有效。
5. **把复用正确性做成可观测指标**：抽样比对"复用输出 vs full prefill 输出"，设误差预算。

### 6.2 给云厂商

1. **多租户隔离与侧信道防护**：前缀缓存默认租户分区/加密；cache key 含权限域；审计"谁读了谁的 KV"。
2. **定义 KV 存储的 SLO 与计费口径**：TTFT 分解、命中率三口径、按 token/按容量计费。
3. **提供 KV 存储的可观测性原语**：trace、命中率、SSD 寿命、慢节点、静默错误。
4. **建设/采用 KV 存储基准**（见 P9）：否则采购与自研都无法公平比较。

### 6.3 给存储厂商

1. **接口从"路径"转向"描述符"**：可 RDMA 注册的 buffer + 异步完成 + 批量提交；POSIX 只是兼容层。
2. **把 KV namespace 作为产品**：命名、版本、租约、GC、多租户配额，而不是只卖带宽。
3. **CXL-SSD 必须软硬协同**：设备可见 KV chunk、claim/commit、布局感知压缩；否则现货无优势。
4. **提供 durability class 与 RPO/RTO 契约**：checkpoint/记忆/KV 的持久性不是布尔值。
5. **把寿命/写放大做成可查询指标**：客户需要按 TBW 做预算。

### 6.4 给研究者：五个最高优先级

1. **KV 复用契约与验证**（P1/P4）：存储层如何表达"可复用"、如何证明、如何失效。
2. **SSD 寿命感知的写入门控**（P3）：写量–命中率–寿命的三元优化。
3. **KV 存储基准**（P9）：块级 trace、reuse distance、故障注入、多租户。
4. **事务型 Agent 记忆**（P6）：R0 数据 + 多写者 + 删除传播。
5. **GPU 直控 I/O 的 QoS**（P2）：多租户下的对象聚合、隔离与尾延迟。

### 6.5 给采购/架构决策者

- 不要按"每 TB 单价"采购 AI 存储；按 **每百万 token 的有效成本**（含 SSD 寿命、网络 egress、缓存命中率、GPU 空转）核算。
- 先确认工作负载类型：**decode 工作集**（必须 HBM/DRAM）vs **prefill 复用缓存**（可 SSD/远端）——二者不能用同一套存储。
- 要求供应商提供 **可复现的 trace 与 baseline**，而不是单一 speedup 数字。

## 7. 结论

2023–2024 年，存储社区解决的是"KV 放不下"的问题：分页、卸载、压缩、前缀复用。2025–2026 年，问题变成了三个更难的：

1. **搬得动吗**——对象粒度、I/O 路径、拓扑感知；
2. **搬得对吗**——复用保真度、版本、失效、误差界；
3. **搬得起吗**——SSD 寿命、egress、TCO、多租户隔离。

这三个问题都不是"把存储做得更快"能解决的，它们要求**把 KV 当作有版本、有生命周期、有正确性契约、有租户边界的一等存储对象**。谁先建立这套抽象，谁就能在下一阶段的推理基础设施中占据定义权。

**最值得下注的三个方向**：KV 对象存储与复用契约、寿命感知的写入门控、KV 存储基准。它们分别对应"正确性"、"可持续性"与"可比较性"——这正是当前领域最缺的三块基础设施。
