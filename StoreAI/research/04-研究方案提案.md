## P1 · KV-OS：带复用契约的 KV 对象存储

**一句话**：把 KV 从"按哈希索引的字节块"升级为"带版本、来源、误差界与失效语义的一等存储对象"，让上层可以问"这份 KV 能不能安全复用"，而不是只能问"命中没有"。

### 问题与证据

- 现有前缀缓存的 key 通常只是 token 序列的哈希，不含模型版本、tokenizer、LoRA adapter、量化配置、RoPE scaling；一旦这些变化，缓存会"命中但错误"，且不报错（`03` 发现 4、发现 10）。
- 非前缀复用的朴素拼接只能保留 37.8%–47.2% 的全量 prefill 答案 [arXiv:2610.15186]；"tolerable set" 表明几何相似度不能预测可用性 [arXiv:2610.22016]。
- 跨上下文/跨 checkpoint 复用已有系统研究：KVShareArena [arXiv:2609.10266] 已将 11 种修复/压缩方法置于同一评测条件下，并从答案质量、prefill 计算、KV 内存与延迟四个视角给出统一口径；但统一的是评测，不是存储接口——它不定义版本化 KV 对象、失效传播与可被引擎调用的复用契约。
- 2026 年缓存侧信道可达 100% 攻击成功率 [arXiv:2608.09225]，说明"谁能复用"本身是安全问题。

### 核心洞察

KV 复用的本质不是"缓存命中"，而是**在某个语义等价类内复用计算**。存储系统应当显式维护这个等价类：哪些维度变化会使 KV 失效（模型、tokenizer、位置、精度），哪些变化只影响误差（量化、稀疏、非前缀拼接），以及误差的界是多少。

### 技术路线

1. **KV 对象模型**：定义 `KVObject = {tensor_ref, model_fingerprint, tokenizer_hash, adapter_id, precision, rope_config, token_span, layer_range, provenance_dag, error_bound, tenant_id}`；数据与元数据分离，元数据用事务型 KV（FoundationDB/etcd）存储。
2. **复用契约 API**：`can_reuse(query_ctx, epsilon) -> {exact | bounded(eps) | must_recompute}`；返回可复用的块列表、预期误差、读取代价估计。
3. **版本与失效**：模型/文档/用户删除触发的级联失效；为每个 KV 块记录依赖的源对象（prompt 片段、文档 ID、模型版本），实现反向索引与删除传播。
4. **存储后端**：本地 NVMe + 远端池（3FS/LMCache/Mooncake Store 均可），支持多级放置与租约；元数据带 MVCC，支持快照读。
5. **安全域**：租户分区、key 含权限域、加密与审计；跨租户共享必须经过显式授权。

### 创新点（相对 SOTA）

- vs LMCache/Mooncake：它们提供"存取"，P1 提供"**可复用性判定**"与失效语义；
- vs SAFE-KV/KVBoost：它们在应用层做修复，P1 把契约下沉到存储层，任何引擎都能用；
- vs KVShareArena：它做评测，P1 做机制与接口；两者互补。
- vs vCache [arXiv:2502.03771]：它在响应级语义缓存上用在线学习阈值给出用户可定义错误率保证；P1 把“误差有界复用”下沉到 KV 对象层，覆盖模型、tokenizer、量化、位置等版本维度。
- vs FinCacheServe [arXiv:2607.26076]：它用文档/证据/工具/模型/解码指纹守卫答案复用，并在其负载上报告零 stale；P1 把同类版本守卫推广到 KV 块，并提供跨引擎接口。

### 评测设计

- 负载：W1 多轮、W2 RAG、W3 Agent；构造"模型更新/文档更新/用户删除"事件注入。
- 指标：M5 命中率（三口径）、M10 任务准确率、**M11 复用保真度**、M12 误差界违反率、M1 TTFT、M9 \$/M-token、M14 隔离度。
- 基线：B1 vLLM APC、B2 SGLang、B4 LMCache、B5 Mooncake。
- 方法：S1 真实 testbed（8×H100 + NVMe + RoCE）+ S2 trace 仿真。

### 预期结果（目标）

- 在同等硬件下，把生产中原本缺乏统一口径的错误复用做成可观测指标；在注入模型更新/文档更新/用户删除事件后，按 M11/M12 度量的错误复用率降到 **<0.1%**；
- 跨模型/跨 adapter 场景下，存储占用降低 **2–5×**（共享基座 + 版本化增量）；
- TTFT 在命中场景下降低 **30–50%**，且 p99 不劣化；
- 删除传播延迟 < 1 s（可审计）。

### 风险与缓解

- 元数据开销：用分层索引 + 批量提交；元数据目标 < 5% 存储字节。
- 与引擎耦合：先做 vLLM/SGLang connector，保持 API 引擎无关。
- 契约过于严格导致命中率下降：提供多档 epsilon，按 SLO 选择。

### 时间线（24 个月）

- M1–M4：对象模型 + 契约 API + 单机 NVMe 原型；
- M5–M9：版本/失效/租约 + vLLM connector + 微基准；
- M10–M16：集群版 + 多租户 + 真实 trace 评测；
- M17–M20：SGLang connector（第二阶段）；
- M21–M24：论文写作 + 开源。

**目标会议**：FAST / OSDI / ATC；期刊 TPDS。

## P2 · GIIO：GPU 直控 I/O 的多租户 QoS 与对象聚合

**一句话**：当 KV 的 I/O 由 GPU 而不是 CPU 发起时，存储系统需要新的"批量描述符 + 租户配额 + 尾延迟隔离"机制，否则只是把 CPU 瓶颈换成 GPU 瓶颈。

### 问题与证据

- Tutti 指出 GDS 仍需 CPU 为每次 I/O 介入，GPU 显存碎片导致海量微小随机 I/O [arXiv:2605.03375]。
- Range 量化了"对象粒度税"：6 GiB KV 切成 6,144 个对象恢复需 3.0 s，而 192 个对象只需 2.1 s [arXiv:2610.21241]。
- 多租户下 GPU 发起的 I/O 会互相干扰；现有工作几乎都假设单租户。
- 拓扑带宽差 72–144×（NVLink vs IB vs TCP）[arXiv:2607.28633]。

### 核心洞察

GPU 直控 I/O 的收益来自"减少 CPU 中介"，但代价是**失去了内核的公平调度与错误隔离**。因此必须把 QoS、配额、错误处理做成设备/驱动层的原语，而不是回到 CPU 路径。

### 技术路线

1. **批量描述符**：一个 doorbell 提交 N 个 KV 块（scatter-gather），支持 layer/head 维度的聚合；与 attention kernel 的流水线对齐。
2. **租户感知队列**：在 GPU 侧/驱动侧维护 per-tenant 队列与信用；用 deficit round-robin 做带宽分配，限制单租户的 in-flight 字节。
3. **尾延迟隔离**：对小 I/O 做合并、对大 I/O 做分片；为 SLO 敏感租户保留带宽。
4. **错误模型**：GPU 发起的 I/O 失败如何传播、重试、降级到重算；提供幂等语义。
5. **拓扑感知**：按 (src,dst) 路径能力选择 NVLink/RDMA/SSD，逐层流水。

### 创新点

- vs Tutti：Tutti 证明单租户可行，P2 解决**多租户 QoS 与错误模型**；
- vs Range：Range 指出对象粒度问题，P2 给出**聚合 + 配额**的系统机制；
- vs 传统 NVMe QoS：把 QoS 从块层提升到**KV 对象层**。

### 评测设计

- 负载：W5 混合在线 + 多租户；W4 长上下文。
- 指标：M1/M2 p99、M3 goodput、**M4 有效吞吐**、M8 元数据开销、M14 隔离度、M13 错误恢复。
- 基线：B1/B3/B5；**B4 明确配置为 GDS-enabled、SSD-backed LMCache（即 Tutti 的对照口径）**；另将 Tutti（strict SLO 下 2× 可达请求率、TTFT −78.3%）与 Range（6 GiB 恢复中位 TTFT 1.79–1.80 s，对照 tuned LMCache 2.12→3.01 s）的报告值列为**单租户参照点**，不与 B1–B5 平级；对照"CPU 发起 + io_uring"路径。
- 方法：S1 testbed + S3 SSD 仿真 + 故障注入（超时、掉盘、ECC）。

### 预期结果

- 单租户：SSD-backed KV 的有效吞吐（M4）相对 GDS-enabled SSD-backed LMCache 提升 **1.5–2.5×**；该区间中位数与 Tutti 已报告的 2× 同量级，因此本方案不把单租户吞吐作为主贡献，而用消融实验分离“GPU-centric 路径”与“对象聚合”各自的增量，并明确标注相对 Tutti 的净增量；
- 多租户下 p99 降低 **40–60%**；
- 单对象 I/O 开销降低 **3–5×**（聚合后；指每对象在查找/分配/提交/投递/写回/索引上的合计开销，对应 M8，非端到端吞吐）。

### 风险

- GPU 侧 I/O 接口受厂商限制（需 CUDA/HIP 支持）；
- 错误处理复杂，可能引入静默数据损坏；
- 需要真实多租户 trace，获取困难。

### 时间线（18–24 个月）

M1–M4 原型（单卡）；M5–M10 多租户 + QoS；M11–M16 集群 + 故障注入；M17–M20 论文/开源。

**目标会议**：OSDI / SOSP / ASPLOS / FAST。

## P3 · LAVA：SSD 寿命感知的 KV 写入门控

**一句话**：把"写多少 KV"与"命中率、读取带宽、SSD 寿命"放在同一个优化目标里，给出可证明的 TBW 预算与写入门控策略。

### 问题与证据

- 多轮对话与 agent 负载下，KV 累计写入量显著超过 SSD 容量，寿命从数年缩短到数月 [arXiv:2610.30791]。
- 急切持久化所有块会迅速耗尽耐久度，而 GPU 服务器 SSD 数量有限又限制重载带宽 [arXiv:2610.31169]。
- LRU 把写入与 miss 耦合，产生过量写流量 [arXiv:2609.07175]。
- 前缀去重能显著削减写量，但依赖 page cache 温热；一旦逐出，683 ms 内发出约 1 GB 顺序读 [arXiv:2610.21249]。

### 核心洞察

KV 写入不是"越多越安全"，而是**用写放大换命中率**。存在一个可观测的帕累托前沿：在给定 TBW 预算下，最大化有效命中（命中且保真）；或在给定命中率下，最小化 NAND 写入。这个前沿取决于 attention 类型、复用距离、SSD 容量/OP、以及读取带宽。

### 技术路线

1. **寿命模型**：`TBW(t) = Σ writes × WA(utilization, GC) `；在线估计每租户/每模型/每层的写入成本。
2. **写入门控**：按"未来复用概率 × 复用收益 / 写入成本"打分；用轻量预测器（序列模型/历史统计）估计复用距离；对低价值块只写元数据或采样写。
3. **介质协同**：ZNS 分区、OP 预留、冷热分离；把顺序写与随机写分流到不同 SSD。
4. **自适应策略**：在线学习写入阈值，目标函数 = 命中收益 − TBW 摊销 − 读带宽成本；支持租户配额。
5. **可观测性**：暴露 TBW 消耗/年、WA、剩余寿命、命中率，供调度器决策。

### 创新点

- vs Gandalf [arXiv:2610.30791]：Gandalf 提出按 attention 类型门控，P3 给出**统一的寿命-命中-带宽三元优化**与 TBW 预算 API；
- vs SARIA [arXiv:2610.31169]：SARIA 用会话局部性，P3 做**跨租户/跨模型的全局配额**；
- vs 传统 SSD FTL：把磨损均衡从设备层提升到**KV 语义层**。

### 评测设计

- 负载：W1/W3/W5；M1–M8 用公开 trace（ShareGPT/Mooncake/BurstGPT/Azure）驱动仿真，同时从 M1 起并行采集 30–90 天生产 trace，仅用于长程复用距离与寿命外推的校准，不阻塞模型与原型阶段。
- 指标：M7 WA/TBW、M5 命中率、M1 TTFT、M9 \$/M-token、M16 能耗。
- 基线：LRU、**Gandalf [arXiv:2610.30791]**（优先作者实现；不可得则按其论文策略忠实复现并标注）、**SARIA [arXiv:2610.31169]**、**admission-controlled LRU-K [arXiv:2609.07175]**、无门控；不以“Gandalf 类/SARIA 类”替代真实系统。
- 方法：S3 FEMU/SimpleSSD 模拟 NAND 写入与 GC，得到 WA(利用率) 曲线；S1 真实 NVMe 用 SMART（Data Units Written、Percentage Used、Media Wearout）做 4–8 周满带宽写入，标定实测 WA 与磨损速率；再按 `寿命 = 额定 TBW / 年化写入量` 外推，并在单一型号上做加速写入以校验外推斜率。所有寿命数字标注为**外推值**，给出型号参数（DWPD、容量、OP）与 95% 区间。

### 预期结果

- 与 Gandalf 在**相同 trace、相同 SSD 型号与容量**上头对头：命中率损失 <5% 时，写入量再降 **30–50%**，寿命增益相对 Gandalf 再提高 **1.5–2×**；
- 相对**无门控基线**，SSD 寿命延长 **2–4×**（外推值；该绝对值不与 Gandalf 的 7.3× 直接可比：7.3× 是其自身 trace 与硬件上的平均值，本文报告同条件相对增益）；
- 写入量降低 **3–5×**；
- 给出可复用的 TBW 预算模型（论文贡献）。

### 风险

- 复用预测误差导致命中率下降；
- 不同 SSD 的 WA 特性差异大，模型需校准；
- 长期 trace 获取困难（可与云厂商合作）。

### 时间线（15 个月）

M1–M3 模型 + 仿真；M4–M8 门控原型 + FEMU；M9–M12 真实 SSD 评测；M13–M15 论文。

**目标会议**：FAST / ATC / ASPLOS；也可投 MLSys。

## P4 · VNPR：可验证的非前缀 KV 复用层

**一句话**：为"文档块出现在任意位置"的复用场景提供带误差界的复用与修复机制，把"能不能复用"从经验判断变成可验证的契约。

### 问题与证据

- 非前缀直接复用会破坏跨 chunk 全局注意力 [arXiv:2605.24022]；
- 朴素拼接只保留 37.8%–47.2% 的答案 [arXiv:2610.15186]；
- 修复可以恢复到 98.4%–100%（SAFE-KV 的 risk-guided K2 selection；[arXiv:2610.15186]），但其 operating rule 在单请求 L40S 研究中退化为 full prefill——忠实修复需重编码大部分上下文。真正的空白因此不是“能否修复”，而是：在给定误差界 ε 下，如何以可验证的触发条件换回部分复用；
- 现有评测会系统性高估复用效果 [arXiv:2609.31415]。

### 核心洞察

非前缀复用的误差不是"渐进的"，而是由**边界 token 与全局注意力**决定的。可以把 KV 块分为"上下文无关的核心"与"依赖前缀的边界"，只对边界做重算；误差界可以由注意力偏差估计，并用小型校验器验证。

### 技术路线

1. **块级依赖分析**：用注意力 rollout/影响函数估计每个 KV 块对前缀的敏感度；标记 core/boundary。
2. **选择性修复**：对 boundary 做 suffix re-encode（SAFE-KV 思路）或 deviation-guided recompute（KVBoost 思路）；优化修复预算。
3. **误差界**：给出 `||output_reuse − output_full|| ≤ ε` 的可计算上界；用采样校验器验证。
4. **存储接口**：KV 块带 `sensitivity` 与 `repair_recipe` 元数据；存储层可按 ε 选择块。
5. **调度**：在 TTFT 与质量之间做 Pareto 选择；支持按请求 SLO 动态调整。

### 创新点

- vs SAFE-KV：它给出修复算法，P4 给出**误差界 + 存储元数据 + 预算调度**的体系；
- vs KVBoost：它用双哈希做匹配，P4 做**敏感度驱动的选择性修复**；
- vs CacheBlend：它做融合，P4 做**可验证性**。

### 评测设计

- 负载：W2 RAG（HotpotQA/2Wiki/NQ）、W3 Agent。
- 指标：M10 准确率、**M11 保真度**、M12 误差违反率、M1 TTFT、修复算力占比。
- 基线：CacheBlend、CacheTune [arXiv:2605.24022]、SAFE-KV、KVBoost、full prefill。需注明：SAFE-KV 的 operating rule 在其单请求 L40S 研究中退化为 full prefill，故“相对 SAFE-KV”与“相对 full prefill”是同一口径。
- 方法：S1 + S2；多种子/多模型（Llama/Qwen/Mistral）。

### 预期结果

- 在保真度（M11：与 full prefill 的逐样本输出一致率）≥95% 下，把重算 token 占比压到 **50–70%**（即相对 SAFE-KV 的 100% full-prefill 口径减少 30–50% 重算），并给出该比例的可达上界；
- 给出可复现的"误差-成本"曲线；
- 在 RAG 负载上 TTFT 相对 full prefill 降低 **2–4×**，同时在同硬件、同负载下与 CacheTune 的 3.72–4.86× 做对照；若低于该区间，需说明是负载/设置差异，还是可证明误差界的保守性所致。

### 风险

- 误差界可能过松，导致保守重算；
- 不同模型/任务的敏感度差异大；
- 评测基准缺乏真实复用动态。

### 时间线（18 个月）

M1–M4 敏感度分析；M5–M9 修复 + 误差界；M10–M14 存储集成；M15–M18 评测/论文。

**目标会议**：MLSys / EuroSys / VLDB；NLP 侧可投 ACL/EMNLP（系统 track）。

## P5 · R2F：在线 recompute-vs-fetch 调度与尾延迟对冲

**一句话**：把"从远端取 KV"与"就地重算"变成两个可对冲的副本，按 SLO 与实时争用动态选择，消灭"远端命中反而更慢"的长尾。

### 问题与证据

- 远端命中 0.88 s vs 重算 0.31 s；16k token 的 p99 从 3.96 s 涨到 17.3 s [arXiv:2610.21500]。但该文的成本模型给出了更强的条件：命中只有在远端带宽超过 B* = sR（该模型/GPU 为 2.53 GB/s）、且 prompt 长于约 17k token 时才划算，更短的 prompt 在任何带宽下都赢不过重算；其 hit-heavy 流上 p99 83.32 s（GPU 仅 7% 忙）主要由同步加载与三个客户端 bug 造成，分片 + 异步加载后降至 0.67 s。
- 静态分层策略必然偏离聚合带宽上界 [arXiv:2610.31827]。
- Cake 已在单请求内把 KV 加载与计算切分并行，用双向调度动态平衡两者，并自适应非前缀请求 [arXiv:2410.03065]；但其目标是最小化平均 TTFT、提高资源利用率，不复制工作、不引入取消，也未对存储/网络尾延迟下的 SLO 违约建模。
- PD 分离后 KV 传输成为关键路径 [arXiv:2607.28633]。

### 核心洞察

Fetch 与 recompute 的延迟分布不同、资源不同（网络/SSD vs GPU），因此可以像"hedged requests"一样同时发起，先完成者胜出；代价是同时浪费一部分算力与带宽。对冲的收益条件必须显式给出：在 SLO 截止时刻 t_d，min(T_fetch, T_recompute) 的 p 分位需显著低于单独 T_fetch 的 p 分位，且 recompute 的尾延迟不严格劣于 SLO——若某类请求（如 <17k token，或带宽充足的长 prompt）已能稳定判定谁更快，就应直接选快者，而不是对冲。关键是联合估计两者的完成时间分布及其交叉点，并据此控制对冲预算。

### 技术路线

1. **延迟模型**：在线估计 fetch 的 p50/p99（按对象数、路径、租户）与 recompute 的时间（按 token 数、模型、GPU 负载）。
2. **对冲调度**：当 fetch 的预测尾延迟超过 SLO 风险阈值时，并发启动 recompute；先完成者取消另一个。
3. **预算控制**：全局对冲预算（额外算力/带宽），按租户/SLO 分配；避免对冲风暴。
4. **对象聚合**：与 P2 联动，减少 fetch 的对象数。
5. **SLO 感知**：按请求优先级选择"保 TTFT"或"保吞吐"。

### 创新点

- vs Mooncake Conductor / Dynamo router：它们做"按命中路由"，P5 做"**按延迟分布对冲**"；
- vs 传统 hedged requests：把对冲从"多副本 RPC"扩展到"计算 vs 存储"两种异构资源；
- 给出可证明的 SLO 违约率上界。

### 评测设计

- 负载：W5 混合在线、W1 多轮；注入网络抖动/SSD 尾延迟。
- 指标：M1/M2 p99、M3 goodput、SLO 违约率、额外算力开销。
- 基线：静态分层、纯 recompute、纯 fetch、Cake 式双向调度（按最优比例切分加载/计算）[arXiv:2410.03065]、Mooncake 风格路由。
- 方法：S2 离散事件仿真 + S1 验证。

### 预期结果

- SLO 违约率降低 **30–50%**；
- goodput 提升 **1.3–1.8×**；
- 额外算力开销控制在 **10–20%**。

### 风险

- 对冲可能加剧 GPU 争用；
- 延迟分布估计偏差；
- 需要真实生产 trace 校准。

### 时间线（12–15 个月）

M1–M3 模型 + 仿真；M4–M8 原型 + vLLM 集成；M9–M12 评测；M13–M15 论文。

**目标会议**：OSDI / NSDI / EuroSys / MLSys。

## P6 · TAMS：事务型 Agent 记忆存储

**一句话**：把 Agent 长期记忆当作 R0 数据，提供 ACID、MVCC、provenance、精确遗忘与多租户隔离，而不是把它塞进最终一致的向量库。

### 问题与证据

- GEM 把记忆正确性定义为"状态轨迹"，提出四算子与六条件，但只是概念框架 [arXiv:2605.26252]。
- ChronoMem 每次写入整库快照，存储放大未量化 [arXiv:2607.27773]。
- Bemula 把遗忘变成一等评测 [arXiv:2610.18052]；现有系统无法精确删除派生摘要。
- 记忆库对 84.7% 的必需应用能检出他人凭证，压力测试下 80–94% 的运行使用他人凭证 [arXiv:2610.25707]。
- 写入放大严重：每次历史数百–数千次 LLM 调用 [arXiv:2610.34673]。

### 核心洞察

记忆不是"文档 + 向量"，而是**带时间、来源、所有权、修订关系的有状态数据集**。它需要数据库的事务与版本语义，也需要文件系统的可读性与对象存储的持久性。三者可以用一个"记忆文件系统 + 事务日志"的组合实现。

### 技术路线

1. **数据模型**：记忆单元 `(id, owner, source_turn, timestamp, content, embedding, provenance_dag, confidence, ttl)`；支持 supersedes 链与 as-of 查询。
2. **事务与 MVCC**：append-only WAL + 快照读；写入批量提交；跨 agent 并发控制。
3. **遗忘与删除传播**：`forget(id | query | time_range)`；派生摘要/索引/embedding 经 `provenance_dag` 级联失效；**存储不变量**：所有持久化派生对象（摘要、embedding、倒排项）必须携带 `source_key_id`，并以源 key 派生的子密钥加密，销毁源 key 即 crypto-shred 其全部后代；不在该密钥树内的副本（备份、导出、第三方）必须登记为残余并单独处理。
4. **索引**：时间范围索引 + 实体-属性倒排 + 向量索引三路并存；查询先路由再检索。
5. **安全**：owner attribution、租户分区、投毒检测（来源家族去重）、访问控制前置到检索层。

### 创新点

- vs Mem0/Zep/MemGPT：它们做检索/抽取，P6 做**事务与治理**——ACID 提交、MVCC 快照读、精确遗忘与多 agent 并发控制；
- vs ChronoMem [arXiv:2607.27773]：它把每次写入提交为整库快照做语义回滚，P6 用 append-only WAL + 增量版本实现原子提交，并把整库快照的存储放大变成可量化、可 GC 的问题；
- vs PolyMemDB [arXiv:2608.25577] / MOSS [arXiv:2607.04391]：前者覆盖 polyglot 存储 + 细粒度 provenance + 时间衰减，后者在关系库上做可审计检索，但都不提供事务原子性、派生数据删除传播与所有权/租户治理；P6 把这些纳入同一事务边界；
- vs GEM [arXiv:2605.26252]：GEM 是愿景（四算子 + 六条件 + MemState 原型），P6 是**可运行的系统 + 基准**；
- vs 传统 DB：把"语义检索"与"事务/版本"结合，是新的数据模型。

### 评测设计

- 负载：W3 Agent 长时程、跨会话；构造删除/回滚/投毒/多 agent 并发。
- 指标：M10 任务准确率、**删除精确率/召回率**、写放大、检索 p99、隔离度、审计完整性。
- 基线：Mem0、Zep、ChronoMem（版本/回滚）、文件式记忆、向量库 + 应用层事务；PolyMemDB 作为 provenance/时间衰减的参照实现（demo 论文，不承担事务基线）。
- 方法：S1 + 真实 agent 轨迹（SWE-bench/WebArena）。

### 预期结果

- 写入次数降低 **3–5×**（批量/异步 consolidation）；
- 精确遗忘：在可定位副本范围内达到 **100%**，并显式列出不可删除残余类型（备份/导出/模型参数中的记忆）及各自的处理策略；在 Bemula 上报告删除精确率/召回率与端到端通过率，不把绝对 100% 作为对外承诺；
- 多 agent 并发下无丢失更新；
- 检索 p99 降低 **30–50%**（三路索引路由）。

### 风险

- 语义索引与事务的结合复杂；
- Agent 负载缺少标准 trace；
- 合规删除的"派生数据"边界难以定义。

### 时间线（18–24 个月）

M1–M4 数据模型 + WAL；M5–M9 索引 + 事务；M10–M14 遗忘/安全；M15–M20 评测/论文。

**目标会议**：SIGMOD / VLDB / OSDI / EuroSys。

## P7 · CaaD：Checkpoint-as-a-Database

**一句话**：把 checkpoint 从"整文件写"升级为"带 manifest、MVCC、GC、跨集群复制的数据库"，支持按层/按专家/按步的增量读取与原子发布。

### 问题与证据

- Checkpoint 是权重的 8 倍（16 B/param），671B 约 10.7 TB；峰均比可达 77×（`analysis-quant.md`）。
- 每步异步检查点的开销在 **1.216B decoder** 上实测为 +656.7% 延迟、32.5 GiB 主机内存、3.39 TB/hour 流量 [arXiv:2609.18178]；该测量规模远小于 671B/千卡级，仅用于说明“异步不等于免费”，不作为 671B 绝对流量的外推依据（671B 体积见上条 16 B/param 模型）。
- TierCheck 用三层放置按故障域优化 [arXiv:2605.17821]；ByteCheckpoint 做并行度无关格式 [arXiv:2407.20143]。
- FailBench 显示"没有机制普遍最优" [arXiv:2610.07688]；控制面（GC/跨集群/原子提交）研究不足。

### 核心洞察

Checkpoint 的生命周期已经超出"容错"：它被选择、合并、审计、甚至电网调度共同消费。因此它更像一个**多版本数据库**：每次 checkpoint 是一个快照，manifest 是目录，增量是 delta，GC 是版本回收，跨集群复制是物化视图。

### 技术路线

1. **Manifest 模型**：`(job, step, layer, expert, dtype, codec, checksum, base_ref, durability_class)`；支持按任意维度定位与组装。
2. **MVCC/GC**：多版本快照、引用计数、血缘 DAG；按保留策略与引用关系回收，避免误删被合并/审计引用的中间态。
3. **原子发布**：对象存储/并行 FS 上的原子 manifest 提交；失败回滚；跨集群复制与一致性校验。
4. **恢复 QoS**：按故障域与 RTO/RPO 选择恢复源（本地/对等/远端）；支持并行度重配置。
5. **安全**：校验和、加密、访问控制、审计；防止 checkpoint 投毒。

### 创新点

- vs ByteCheckpoint：它做格式/重分片，P7 做**控制面与多版本语义**；
- vs TierCheck：它做放置，P7 做**生命周期与 GC**；
- vs 传统备份系统：面向"训练状态"的细粒度与并行恢复。

### 评测设计

- 负载：W7 训练（模拟 1k–10k GPU）；故障注入（单点/机架/级联）。
- 指标：M13 RTO/RPO、写放大、恢复读带宽、GC 开销、存储放大。
- 基线：PyTorch DCP、ByteCheckpoint、TierCheck、对象存储整文件；恢复时间另设 FFTrainer [arXiv:2512.03644] 为 SOTA 参照（摘要称最多降低 98% 恢复时间，但依赖剩余网络带宽、故障模型与 P7 不同，单列口径，不作跨论文换算）；写入放大另设 LLMTailor [arXiv:2602.22158] 与差分检查点 [arXiv:2509.04084] 为参照。
- 方法：S2 仿真 + S3 SSD + S1 小规模验证。

### 预期结果

- RTO 降低 **50%**（相对 DCP/ByteCheckpoint/TierCheck/整文件基线；若与 FFTrainer 同场，限定在相同故障域并计入 manifest/GC 开销，或改报 FFTrainer 不覆盖的跨集群/级联故障域，不把其 98% 的 “up to” 当作下界）；
- 写入放大降低 **3×**（增量 + 去重）；
- 跨集群恢复时间降低 **2×**；
- GC 误删率 0（可证明）。

### 风险

- 训练框架耦合深；
- 对象存储原子性弱；
- 大规模故障注入成本高。

### 时间线（18 个月）

M1–M4 manifest + 格式；M5–M9 MVCC/GC；M10–M14 跨集群/恢复；M15–M18 论文。

**目标会议**：FAST / ATC / VLDB / SC。

## P8 · MSC：模型供应链存储

**一句话**：为"基座 + 大量 LoRA/量化/微调变体"设计内容寻址、增量分发、读时转码与供应链安全的模型存储层。

### 问题与证据

- 模型变体爆炸导致存储放大；safetensors 是事实标准但无系统级去重/版本语义。
- HuggingFace Xet 用 blob 级 CDC 去重，但不提供张量级变体语义与读时转码。
- 运行时层已有系统研究：Tangram 用 GPU 内存池做张量级跨模型参数共享 [arXiv:2512.01357]，gKSM 在驱动层做权重去重 [arXiv:2610.25219]，ServerlessLoRA 让多个 LoRA 只读共享同一 backbone [arXiv:2505.14468]，TensorCast 提供张量生命周期抽象层并已与 vLLM/SGLang 集成评测 [arXiv:2608.06007]。缺口在**存储层**：跨变体的可寻址 delta、张量级内容寻址与读时转码尚无系统工作。
- 跨变体 KV 复用存在语义漂移 [arXiv:2609.10266]。
- 机密计算下 DMA 假设失效，吞吐损失 13–27% [arXiv:2606.23969]。

### 核心洞察

模型不是"一个大文件"，而是**按张量组织、跨变体高度共享、需要按需转码的内容集合**。存储层应以张量为单位做内容寻址与 delta，而不是以文件为单位做复制。

### 技术路线

1. **Canonical tensor store**：按 `(base_model_hash, tensor_name, shard, dtype)` 内容寻址；张量级 CDC 去重。
2. **变体 delta**：LoRA/微调/量化的增量表示；读时转码（dequantize/merge）在加载路径完成。
3. **分发**：P2P/多播、range 读、按层预取；execute-while-load。
4. **供应链安全**：Merkle 校验、签名、SBOM、访问控制；防止权重投毒。
5. **GC/保留**：引用计数 + 血缘；跨仓库去重。

### 创新点

- vs Xet：Xet 做 blob 级 CDC，P8 做**张量级语义 + 读时转码**；
- vs safetensors：格式标准，P8 做**存储系统**；
- vs Tangram/gKSM/ServerlessLoRA：三者在 GPU 显存、驱动、服务层做运行时共享，P8 在**存储层**做内容寻址与跨变体 delta，互补而非替代；
- vs TensorCast：TensorCast 是运行时的张量生命周期层（已实现并与 vLLM/SGLang 集成评测），P8 做**持久化存储层的张量寻址、delta 与读时转码**。

### 评测设计

- 负载：100 个变体（base + LoRA + 量化）、冷启动、跨仓库。
- 指标：存储放大、冷启动延迟、加载带宽、去重率、校验开销。
- 基线：safetensors 全量复制、Xet、OCI artifact、TensorCast 权重物化路径 [arXiv:2608.06007]。
- 方法：S1 + 真实模型仓库 trace。

### 预期结果

- 100 个 70B 变体从 14 TB 降到 **~181 GB（约 77×）**：按 1 份 fp16 基座 140 GB + 99 个 rank-16 all-linear LoRA（bf16，约 0.41 GB/个，共 ~41 GB）计；LoRA 取 rank-8/32 时分别约 160 GB（~87×）/222 GB（~63×）。
- 冷启动降低 **30–50%**（基线：safetensors 全量复制；P-LoRA 的 68% 是 adapter 从 host 预取到 GPU 的口径 [arXiv:2512.20210]，不与本指标直接比较）；
- 供应链校验开销 <5%。

### 风险

- 读时转码增加加载 CPU/GPU 开销；
- 跨框架格式差异；
- 安全与性能的权衡。

### 时间线（15 个月）

M1–M3 格式/索引；M4–M8 delta + 转码；M9–M12 分发/安全；M13–M15 论文。

**目标会议**：FAST / ATC / MLSys。

## P9 · KVBench：KV 存储的标准基准与可观测性

**一句话**：建立第一个面向存储层的 KV 基准——覆盖块级 trace、复用距离、多租户、故障注入与寿命/TBW，补上 KVShareArena 等方法级评测、KV-Repurpose 等单系统 testbed 未覆盖的存储指标与跨系统比较。

### 问题与证据

- 14 种驱逐算法相对 LRU 提升有限，20 种混合负载下没有单一最优 [arXiv:2609.28870][arXiv:2610.36355]。
- 压缩组合不叠加 [arXiv:2610.33076]；FailBench 显示 checkpoint 机制无普适最优 [arXiv:2610.07688]。
- 现有评测会系统性高估复用效果，数据集缺乏真实复用动态 [arXiv:2609.31415]。
- MLPerf Storage 覆盖训练数据/checkpoint，不覆盖推理 KV；ANN benchmark 不覆盖过滤/多租户。

### 核心洞察

领域缺的不是又一个系统，而是**可复现的测量基础设施**。没有统一的 trace 格式、命中率定义、SLO 口径与故障模型，所有 speedup 都不可比。

### 技术路线

1. **Trace 格式**：请求到达、token 序列、prefix graph、KV 块访问、复用距离、租户、SLO；支持脱敏与合成。
2. **负载套件**：W1–W7；真实 trace（Mooncake/BurstGPT/Azure）+ 合成生成器。
3. **指标库**：M1–M16 的标准实现；三种命中率口径；尾延迟统计。
4. **故障/寿命注入**：SSD 掉盘、网络抖动、GC 抖动、TBW 耗尽。
5. **参考实现**：vLLM/SGLang/LMCache/Mooncake 的 adapter；一键复现实验。

### 创新点

- 第一个**以 KV 存储层为中心**的存储基准：KVShareArena [arXiv:2609.10266] 已为复用方法提供统一接口与 leaderboard，KV-Repurpose [arXiv:2610.13060] 提供 vLLM 上的单系统 testbed，Boxoffice [arXiv:2609.31415] 提供复用数据集生成；但三者均不测块级 trace、复用距离、寿命/TBW 与存储设备级故障注入，也不做跨系统排序；
- 把**正确性/保真度**纳入基准（M11）；
- 把**寿命/TBW**纳入基准（M7）。

### 评测设计

本身即评测方法；用 5–10 个系统做 case study，证明排序与真实部署一致。

### 预期结果

- 可测目标：同一 trace 下 5 个系统的排序与各自论文报告一致（或差异可解释）；
- 复现一个已发表系统结果所需人时从 X 降到 Y（v0.1 先给出 X 的基线测量）；
- 揭示 3–5 个"论文收益在真实 trace 下消失"的案例。

### 风险

- 真实 trace 获取困难（需产业合作）；
- 基准可能被"刷分"；
- 维护成本高。

### 时间线（12 个月，交付 v0.1）

12 个月只承诺 **v0.1**：trace 格式、3 个负载、4 个核心指标 + 最小可观测性、2 个 adapter、3–5 系统 case study 与短文；W1–W7 / M1–M16 全覆盖、5–10 系统与正会全文放到第二阶段。

- M1–M3：trace 格式 v0.1 + M1/M5/M7/M11 的标准实现与三种命中率口径；
- M4–M7：W1/W2/W5 三个负载 + 合成生成器；故障/寿命注入原型（FEMU）；
- M8–M10：vLLM 与 LMCache 两个 adapter 与一键复现脚本；
- M11–M12：开源工具链 + 3–5 个系统的 case study + measurement track 短文。

**第二阶段（M13–M24）**：补齐 W3/W4/W6/W7、其余指标、SGLang/Mooncake adapter、5–10 系统 case study 与正会全文。

**目标会议**：FAST / MLSys / NSDI（measurement track）；也可作为社区项目。

## P10 · CXL-KV：CXL-SSD 的设备语义与 KV 引擎

**一句话**：现货 CXL-SSD 不比 NVMe 快，除非把 KV chunk 变成设备可见的 I/O 单元，并让设备参与 claim/commit、压缩与预取。

### 问题与证据

- 现货 CXL-SSD 比本地 DRAM 慢约 3×，且不比 NVMe SSD 更快 [arXiv:2609.26828]。
- CXL 链路带宽远低于 HBM，需布局感知压缩 [arXiv:2509.03377]。
- TempoKV 用 claim/commit 解耦"知道会复用"与"占住快层" [arXiv:2609.35065]。
- 光子 CXL 可降低池延迟 >50%（emulation）[arXiv:2607.27187]。

### 核心洞察

CXL 的价值不在"更快的 SSD"，而在**设备可参与语义决策**。但这一判断已由 LM-CXD 用"设备可见 chunk + NAND→DRAM 进度暴露 + 设备 DRAM 缓冲"实现（TTFT 相对 stock CXL-SSD 最高 4.03×），并由 TempoKV 用 claim/commit 实现；P10 不再把这两条机制当作自身创新，而是在其之上补两块空白：**多租户 QoS（带宽/容量配额、尾延迟隔离）**与**设备内 KV 专用压缩**，并给出"何时 CXL-SSD 值得"的判据。

### 技术路线

1. **复用设备可见 chunk 接口**：采用 LM-CXD 的一等 I/O 单元、NAND→DRAM 进度与 resident 状态暴露，作为 P10 的基础层而非创新点 [arXiv:2609.26828]。
2. **复用 claim/commit 协议**：采用 TempoKV 的元数据认领、到期提交与受保护容量语义；P10 仅新增跨租户的受保护容量仲裁 [arXiv:2609.35065]。
3. **布局感知压缩**：channel-major/bit-plane、KV 专用变换；压缩在设备内完成。
4. **QoS**：多租户的带宽/容量配额；尾延迟隔离。
5. **仿真/原型**：gem5+CXL 模型 + FPGA/真实 CXL 设备。

### 创新点

- vs LM-CXD：复用其设备可见 chunk 机制；P10 的增量是**多租户 QoS + 设备内压缩 + 端到端 KV 引擎**，不是设备接口本身；
- vs TempoKV：复用其 claim/commit 时序语义；P10 的增量是**跨租户受保护容量仲裁与压缩感知的 commit 估计**；
- vs TRACE：它做压缩原语，P10 做**压缩与 QoS 的联合调度**。

### 评测设计

- 负载：W1/W4/W5；CXL-SSD 仿真 + 小规模硬件。
- 指标：TTFT/TPOT、有效带宽、压缩比、设备利用率、尾延迟。
- 基线：NVMe SSD、DRAM、stock CXL-SSD、**LM-CXD**、**TempoKV**（复现或按其公开配置对齐）。
- 方法：S4 仿真 + S1 原型。

### 预期结果

- TTFT 相对 stock CXL-SSD：在同配置（layerwise prefetch）下不低于 LM-CXD 的 **4.03×**；若负载导致绝对值不同，须给出 LM-CXD 在同一负载下的复现值作为对照，并解释差异来源；
- 多租户 SLO：租户过载时 p99 TTFT 降低 **≥50%**，租户间有效带宽偏差 **≤10%**（LM-CXD/TempoKV 未覆盖的指标）；
- 给出"何时 CXL-SSD 值得"的判据。

### 风险

- **设备侧可编程性（关键前置）**：设备可见 chunk、NAND→DRAM 进度上报、受保护容量与设备内压缩都要求改控制器/固件；现货 CXL-SSD 不暴露这些接口。缓解：M1–M3 评估 CXL-FPGA 原型链路，M4–M6 设 go/no-go gate；若不通过，退化为 host 侧 hint + 块层 QoS，不承诺 claim/commit 与设备内压缩。
- **真实设备与厂商合作**：M15–M20 若要在真实 CXL-SSD 上验证，须提前锁定能提供固件/接口支持的厂商；否则硬件评测限定为 FPGA 原型 + stock CXL-SSD 基线。
- **仿真与真实差距**：gem5+CXL 模型须用 FPGA 原型校准，分别报告仿真/原型/现货三档数字。

### 时间线（24 个月）

M1–M3 仿真/接口 + 设备可编程性评估；M4–M6 go/no-go gate + 接口定稿；M7–M14 FPGA 原型；M15–M20 硬件评测（以 FPGA 原型为主，真实 CXL-SSD 视厂商合作）；M21–M24 论文。

**目标会议**：ASPLOS / ISCA / MICRO / FAST。

## P11（探索）· Hybrid-State Store：混合/线性注意力的状态存储

**问题**：线性注意力/混合架构的 recurrent state 无法回滚到任意前缀，现有前缀缓存抽象失效 [arXiv:2609.33477]；Tail-Replay 用有损压缩绕开 [arXiv:2608.30310]。

**想法**：把状态定义为"可检查点化的分段函数"，存储层维护离散检查点 + 重放日志；查询时按最近检查点 + 重放恢复。需要新的状态快照格式、重放代价模型与 GC。

**为什么现在做**：2026 年混合架构开始规模化，存储抽象尚未跟上；先发优势明显。

**风险**：模型架构仍在快速演化；可能需要与模型团队深度合作。

---

## P12（探索）· 多模态/视频生成存储

**问题**：视频扩散模型的 latent、时序激活、世界模型状态体积大、生命周期长、可重建性低；现有 KV 缓存抽象不适用。

**想法**：时序 latent 的分层缓存 + 内容寻址去重 + 镜头/场景索引；训练侧需要高吞吐 latent 存储，推理侧需要低延迟读取。

**为什么现在做**：视频生成在 2025–2026 快速增长，存储需求尚未被系统研究。

**风险**： workload 不成熟；缺乏公开 trace。

## 结语

这 10 个方案有一个共同点：**它们都不是"把某个现有系统做得更快"，而是为 KV/记忆/checkpoint 建立新的存储抽象**。这正是 2026 年之后最稀缺的能力——当算力与带宽的边际收益递减时，定义"数据如何被组织、复用、验证、删除"的系统，会比再优化一个 kernel 更有价值。
